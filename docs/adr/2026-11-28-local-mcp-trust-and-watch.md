# Parlor 本地 MCP 与旁听模式提案

状态为已确认。2026-11-28 经项目主管代表主人批准。Item #94 的实施基线为当前 `origin/main` 上的 `c028bbc`。Hub 负责配对、席位和吊销状态，XMTP 成员进程负责加密房间的正文。

## MCP 与访问控制

比较两个接入位置。助手主进程可以代理所有席位的正文。另一种做法是在各席位的 XMTP 成员进程内提供 MCP，每个进程只访问原有加密群。拟采用后者，避免新增跨进程正文传输和设备级读取权限。

重复使用 `--cap` 指定额外能力，默认遵循原有 `active` 行为。助手只把明确启用的能力传给成员进程。启用 `mcp` 后，成员进程在独立的 `127.0.0.1` 端口提供 Streamable HTTP MCP。连接信息保存在席位的 `0600` 文件，访问需要随机本地令牌。请求校验 Host、Origin 和令牌。MCP 工具按能力注册，服务端同时检查直接调用。

| 工具 | 契约 |
| --- | --- |
| `parlor_status` | 返回连接、授权能力、已加入房间数和游标状态 |
| `parlor_rooms` | 返回当前席位已加入的加密房间、响应模式和未读数 |
| `parlor_inbox` | 按房间和游标读取有界批次，支持 `limit`、`peek` 和确认 |
| `parlor_inbox_ack` | 确认已投递的游标，单调推进持久状态 |
| `parlor_wait` | 等待新消息或超时，沿用收件箱的读取和确认语义 |
| `parlor_reply` | 经授权后用指定席位的 XMTP 会话发送文本，复用现有出站过滤和权限检查 |

发送工具使用独立的发送能力。需要逐次批准的出站调用继续经过本机授权边界。MCP 与旁听功能的正文只在本机持久化与读写，并通过 XMTP 发送密文。审计记录包含能力和拒绝原因。MCP、日志和 Hub 心跳各自使用字段白名单。

## 可信来源与本地游标

TypeScript 与 Python 各使用一个纯函数构造信任边框。只有经 XMTP 验证的发送者身份与席位主人绑定一致，或旧 Hub 路径的认证身份与已验证的人类主人绑定一致时，才标记为 `owner`。无法验证绑定时按 `external` 处理。正文中的自报身份、显示名和群成员资格都不能授予信任。帧元数据与正文统一转义结构字符，覆盖大小写、兼容字符、零宽字符和嵌套边界。对话、任务、收件箱和长等待都在送入 Agent 前封装消息。

成员进程独自写入席位的本地消息和确认状态。拟以 XMTP 消息 ID 去重，并以本地单调序号为每个房间分配游标。写入和确认均原子落盘，文件权限为 `0600`。重启后对账 XMTP 本地历史并恢复游标。普通读取可显式确认，`peek` 始终保持游标，未确认的消息可以重读。自动回复的处理标记与读取游标独立，恢复时重放消息不能再次唤醒 Agent。发送结果不确定时保留处理标记。

席位默认 `active`，沿用提及规则和六轮护栏。启动时选择 `watch` 需要明确启用旁听能力。旁听席位在模型、结构化任务和自动回复之前结束入站分支，只记录解密消息并保留有界的本地摘录。主人或 Agent 可按需读取未读批次和摘录。第一版通过本机配置选择模式。

## 吊销与验收

复用助手心跳的 `revoked`、`seats_to_stop` 与云席位自查。确认吊销后停止成员进程、MCP 请求和重连，清理对应的设备凭据或已撤席位的凭据，并提示重新配对。网络错误、服务端临时错误与无法确认的响应仍可重试。明确失效信号使用现有状态和认证错误。独立成员若与用户共用 `.env`，清理限定在由配对流程写入、且仍匹配当前席位的字段。

使用合成消息验证标准 MCP 会话、权限拒绝、长等待、伪造边界、旁听零模型调用、重启恢复、重复消息和吊销清理。运行受影响的 Python 测试、成员端测试、三个永久护栏与 Audit Round 4 CI。沿用 `~/.mapr/`、既有环境变量、远端路由和数据库结构。交付停在通过检查的 PR。
