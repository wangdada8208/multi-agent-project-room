## 2. 产品目标与最小范围

目标：两位主人各自拥有一个本地 Agent，通过 Hub 交换经授权的信息并协商结果。连接只允许通信，不自动授予读取私有数据、执行工具或代表主人作出承诺的权限。

首个场景建议使用**虚构日历协调候选时间**：

1. 两边主人分别授权自己的 Agent 参与指定会话。
2. 每边只允许交换明确批准的空闲时间段。
3. Agent 提出候选时间；超出授权时暂停并请示。
4. 主人可拒绝、撤销或停止；结果向各自主人的私有界面汇报。
5. 不创建真实日历事件；正式邀请和日程写入属于后续独立动作及授权。

最终验收应观察可验证行为，不以聊天流畅、出现“已达成共识”或 CLI 正常退出代替任务成功。

## 4. 身份：认证之后还要知道“代表谁”

建议建立明确关系：`owner_id → agent_id → runner_id/credential → conversation membership`。

- 第一版可以采用可信签发的 token，不必立即采用公私钥体系。
- 写明首次登记、主人确认绑定、凭据签发、轮换与撤销流程；Runner 自行生成随机 token 不构成可信注册。
- 服务端从凭据解析主体，不接受正文中的名字作为身份依据。
- 每次访问都验证会话成员关系、房间范围和动作权限；登录用户不应因此能够冒用其他 Agent。
- 先明确 Hub 是受信中继还是不可信中继。建议 MVP 明确按受信中继设计，使用 TLS；这不是端到端加密承诺。

源码注意：远端 `handle_dialogue_jsonrpc()` 校验登录后调用 `handler(request.params)`，尚未把已认证主体带入 handler。应将认证上下文显式传入，并按身份检查 start/send/end/status 等操作。

## 5. 授权：审批申请与有效权限分开建模

审批记录说明“有人做过决定”；有效授权说明“当前这个主体，可以对这个对象执行这项动作”。两者关联但不等同。

建议第一版先做一次性授权，至少明确：授权主人、执行 Agent、会话、对端接收者、动作、允许的数据字段、请求内容版本或摘要、有效期、撤销时间、使用状态。存储形式与迁移方案需要单独评审，不在本文直接决定数据库结构。

执行顺序建议为：

`收到外部请求 → 验证身份/范围 → 构造结构化动作 → 查授权 → 必要时请示 → 执行前复核 → 执行动作 → 持久化结果 → 授权范围内汇报`

- 主人的拒绝与撤销都必须是可执行状态，不能仅附在 prompt 中。
- 批准必须绑定具体请求版本；请求改变后，旧批准不得自动复用。
- 本地数据读取、外部工具动作、消息出站分别检查权限。
- 在生成回复后、真正发送前复核授权，减少生成期间撤销造成的信息泄露。
- 单次授权的消费要防并发；外部动作与本地账本不能原子提交时，按“结果待核实”处理不确定结果，不能盲目重试。
- 对已经发送的信息无法承诺撤回；撤销应阻止后续动作，并向主人说明已发生部分。

当前旧适配器在调用本地 AI 后才根据关键词创建审批。如果 CLI 有工具权限，真实动作可能已发生。审批必须下沉到执行器或工具边界；不要依赖模型自愿输出“需要审批”。

## 6. 可靠通信：重发消息不能重复执行动作

建议保留 Hub 中继路径，先统一现有执行入口，避免未经论证新增一套平行协议栈。

最小信封可包含：`protocol_version`、`message_id`、`conversation_id`、`sender_id`、`recipient_id`、`sender_seq`、`reply_to`、`message_type`、`created_at`、`expires_at`、结构化 payload。身份字段必须与认证上下文一致。

- `sender_seq` 按会话及发送方分配并持久化；发送时间用于审计，不替代顺序控制。
- 收件箱持久化成功后才确认接收；处理失败不等于未收到。
- 发件箱保留待确认消息，断线重试保持相同 ID 和内容；相同 ID 不同内容应拒绝。
- 持久化去重键和处理状态，区分“已接收”“已处理”“动作完成”。
- 明确乱序、缺号、重复确认、消息过期及重连对账规则，并限制重试次数、并发、队列大小和保留期。
- 动作具有独立幂等键。执行后崩溃且结果不明时，先核实外部状态；不能用消息重发直接触发第二次执行。

当前对话仍保存在进程内 `DIALOGUES` 中；重启后不能仅靠聊天记录恢复。`_save_room_message()` 落库失败后仍返回临时消息，发送路径还可能继续广播并返回成功。可靠协议应明确拒绝持久化失败，或返回可恢复失败状态，不得以临时广播代替持久确认。

自动循环还存在落库消息与广播消息分别生成 ID 的路径。后续应广播已持久化的同一消息对象，以支持统一去重、回放和确认。

## 7. 会话、暂停、恢复与打断

建议将会话生命周期与单条消息投递状态分开。会话可考虑：`active`、`waiting_owner`、`canceling`、`completed`、`canceled`、`failed`、`expired`；含义和允许转移在实施前固定。

- 会话记录主题、参与身份、当前轮次、待处理动作、批准请求、版本和时间预算。
- 消息分别保存 `conversation_id` 与 `reply_to_message_id`，不要继续把会话 ID 与父消息 ID 混用。
- 对轮次使用原子版本检查，防止双方同时回复、重发推进两轮或旧消息恢复已结束会话。
- 主人答复后恢复同一个动作和会话；进程重启后从持久状态恢复，不依赖一次广播。
- 等待主人时明确超时政策：执行超时可以暂停，但授权有效期仍按真实时间计算。
- 轮次数、模型调用数、墙钟时间和费用预算分别约束；文本长度或轮数不能替代成本控制。

当前 WebSocket 回复携带 `task_id` 时会调用 `complete_task()`，后者直接写 completed。请求审批的回复可能覆盖等待状态，迟到结果也可能覆盖已取消状态。应先定义并执行状态转移约束，回复消息与完成事件分开处理。

打断需要独立控制通道：接收循环持续运行，执行器单独工作；取消后停止启动动作，尽力终止进程及子进程，并丢弃旧执行版本的迟到输出。旧适配器即使使用 `asyncio.to_thread()`，接收循环仍等待该处理函数结束，不能据此声称即时响应主人。

远端自动循环在等待 `_send_to_agent()` 返回后直接记录和广播结果，仍应补“返回后再次检查取消/版本”的关卡。外部已完成的副作用如实汇报，不能承诺终止进程等于撤销一切。

## 8. 数据边界与可信汇报

先约束数据进入模型和工具的范围，再校验出站结构；不要先给模型完整私人资料，再期待输出过滤兜底。

- 空闲时间场景只发送获批时间段和必要时区，不发送日历标题、备注、地点或其他参与者。
- 对方消息是外部输入，不是系统指令，也不是主人的新授权。
- Hub 当前会保存并向房间广播内容。需要明确主人私有消息、双方共享消息以及房间其他成员的可见范围。
- 主人请示走私有渠道；共享房间只显示最少必要的等待状态。
- 日志、错误、模型输出同样受数据范围约束，不记录凭据或完整私人内容。
- 明确保留期限、删除与审计策略；“用完即归档”不等于删除，也不能保证对方不再使用。
- 本方可以强制约束本地读取和发送；对端收到后的用途限制属于约定或对端控制，不能写成我方代码可保证的事实。

结果汇报应包含：提出过什么、批准了什么、实际交换了什么、双方明确确认了什么、是否产生外部动作、尚未解决什么。`[CONSENSUS]` 只能作为提示，不能替代双方对同一提案版本的结构化确认，更不能替代主人授权。

## 9. 分阶段实施与验收

### Phase 0：统一基线和约定

产出：固定 commit、执行路径图、能力对照、失败清单、测试/构建报告及关键耗时测量。补齐 v0.3 来源，确认旧适配器、网关、Hub 循环和本地调度器各自保留或迁移的职责。

验收：合作者从同一版本能重现结果；历史测试与本轮测试明确区分；不将文档勾选当作运行证据。当前本文尚未完成这一阶段的全部测量和新版本运行验证。

### Phase 1：Mock 条件下建立可信通道

产出：认证与主人绑定、会话权限、持久化收发/去重、结构化一次性授权、状态转移与取消控制。先单机两进程验证，再用两台机器验证真实断线恢复；不使用真实私人数据或付费模型执行动作。

验收：未经授权的消息不能进入执行；重发不重复动作；重启恢复状态；主人停止后无新的动作及迟到输出泄露。

### Phase 2：接入真实模型完成有限协作

产出：虚构日历协商完整闭环，包含批准、拒绝、撤销、继续与最终汇报。之后再单独评审真实数据接入与外部写入。

验收：两位主人各自控制自己的 Agent；每次披露和动作可关联授权；结果可核实；模型调用和预算有记录。

## 10. 必须覆盖的失败场景

| 场景 | 预期结果 |
| --- | --- |
| 无效/已撤销凭据、冒用其他 Agent、访问非成员会话 | 拒绝，不泄露会话内容 |
| 错误主人批准、批准后修改请求 | 拒绝或重新申请，旧批准不复用 |
| 重复消息、乱序、丢失确认 | 可对账恢复；轮次和动作不重复 |
| 落库失败、Hub/Runner 重启 | 不假报已接收；可恢复或明确失败 |
| 动作已执行但结果未记录 | 标记待核实，不盲目重跑 |
| 等待主人后断线/重启 | 恢复同一请求，批准只生效一次 |
| 生成期间撤销、执行中取消、迟到结果 | 禁止新增动作和过期回复；说明已发生部分 |
| 对方消息要求忽略规则或披露其他资料 | 不扩大权限，记录拒绝原因 |
| 单方声称共识、模型失败、预算耗尽 | 不伪造双方同意；明确结束或升级请示 |
| 新认证与旧客户端混用 | 明确报认证失败，不假报注册/运行成功 |

## 11. 合作实施顺序与变更边界

建议先由双方确认职责和状态契约，再分模块实施：

1. 固定远端基线与客户端兼容路径，补身份/会话访问检查。
2. 处理审批前执行和终态被覆盖的问题。
3. 实现持久会话、收发确认、去重和恢复。
4. 接通取消、等待主人后的恢复与私有汇报界面。
5. 完成 Mock 故障验收，再接入真实模型和两台机器。

可复用现有模块，但这仍可能涉及架构和数据库迁移。按项目约定，对实际架构/数据库更改另行形成可审阅提案并取得批准；本指导文档的发布不等于批准任何具体迁移、主分支合并或生产部署。

仓库已包含 A2A SDK 路径，因此原文“协议全部自定，标准仅参考而非依赖”不应继续作为现状描述。后续先列明标准能力、项目扩展和兼容约束；不因采用 SDK 就推定身份、可靠投递和业务授权自动解决，也不为了“每行自己写”而重复实现已有能力。

本次交付仅为文档改写与发布，不包含运行代码变更。后续实施需以实际测试、双机故障演练和授权审计支撑完成结论。
