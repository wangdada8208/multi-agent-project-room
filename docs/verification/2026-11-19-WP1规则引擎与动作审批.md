## 交付内容

### 三档裁决（rulesEngine.ts 新文件）

- `decide(rules, policy, {actor, kind, scope})` → `allow|ask|cannot` + `rule`（命中规则描述，写审批卡与账本）。
- 裁决顺序：硬禁区 → 单 actor 覆盖 → house scope 规则 → 旧 allow 白名单（仅 data，映射 ask）→ `house["*"]`（默认 ask）。
- 硬禁区：`payment./banking./credentials./password./card./wallet.` 前缀 + `data.export_all`，任何规则都改不了。
- 旧 `policy.allow` 语义保持「允许请示」，**不会**升级成自动放行——老行为不会悄悄变松。
- `policy.rules`：`{house: {scope: decision}, actors: {addr: {scope: decision}}}`，存 `.state/policy.json`（0600），`normalizePolicy` 归一化。

### 审批闭环

- ConsentQueue 扩字段：`kind:"data"|"action"`、`params`、`params_hash`、`rule_hit`、`expires_at`（data=10min/action=24h）、`decided_at`。旧 consents.json 加载时自动补齐，无损。
- 新信封：`action_request`（action+params+purpose，params≤8KB）、`action_result`（签名 grant+params_hash+status:executed/failed/uncertain+receipt+summary）。pending 通知复用 `consent_pending`（比计划里的 `action_pending` 少一个 kind，协议更瘦）。
- DenialReason 增加 `cannot`（规则直拒，区别于 out_of_scope 的「服务不了」）。
- `handleEnvelope`：
  - `request`（数据披露）：先规则裁决再可服务性校验。`cannot`→denial(cannot)；`allow`→autoApprove 走与人工批准完全相同的路径；`ask`→queue+consent_pending。
  - `action_request`：同上，另查 `canExecuteAction`（无连接器→out_of_scope）。
  - `action_result`：`verifyGrant`（expectedPayloadHash=params_hash）验签+归属+过期→存 inbox。
  - `autoApprove` 失败落回 pending 等人工，不丢请求。
- `consentActions.runApprovedAction`：批准时先校验 `params_hash===hash(params)`（队列文件被手改→拒执行记 `action_tampered`）→ 找有 `execute` 的连接器（无→releaseApproval 回 pending）→ execute（抛错→receipt=uncertain，**不自动重试**）→ buildGrant(payload=params，payload_hash 即 params_hash)→签名→`action_result` 回执。发送失败只记账本不回退审批（重批=二次执行红线）。
- `verifyGrant` 支持 `expectedPayloadHash`（action_result 只带哈希不带原文）；`isGrant` 接受空日期对 `{date_from:"",date_to:""}`（动作批准无时间范围语义）。
- ownerConsole 审批卡：动作类显示「【动作】+动作名+参数预览（≤300字符）+触发规则+到期时间」，数据类维持原文案。

## R0 复审修订（2026-11-19 同日追加）

独立复审（`/data/.qoder-cn/plans/distant-timber-bull.md` 步骤 1）对本包提出 R0 级问题，
以下逐条对修并重新实测。原 WP1 段落中与本节冲突的描述以本节为准。

### 复审发现 → 实际修复

- 「autoApprove 失败可留下 approved/pending 矛盾 + 对请求方谎报 consent_pending」
  → ConsentQueue 改为可判别状态机 `pending/approved/executing/awaiting_receipt/completed/denied/expired/uncertain`，
  迁移表受限、终态无出边；`consent_pending` 只在条目仍停 pending 时才发。
- 「执行/回执不分，回执发送失败可能引发重复执行」
  → `runApprovedAction` 在 connector.execute 前先落 `executing+attempt_at`；已签名回执先持久化进
  `outbox` 再发送；发送失败停 `awaiting_receipt`，`resendReceipt`（上限 10 次）只重发 outbox 原文、
  绝不重新 execute；connector 抛错落 `uncertain` 终态（外部副作用不明，需人工对账）。
- 「重启后 executing 状态语义不明」
  → `queue.recoverAfterLoad()` 把 executing ⇒ uncertain 并记 `recovered_uncertain` 账本，绝不自动重放。
- 「回执/披露与请求不绑定，攻击者可自签 grant 伪造 action_result」
  → 新增 `outgoingRequests.ts` 出站请求登记（request_id+预期响应者+scope/action+canonical 参数哈希+有效期，
  0600 原子写）。`action_result`/`disclosure` 必须匹配登记条目（unknown_request/wrong_responder/
  kind_mismatch/scope_mismatch/hash_mismatch/request_expired 一律拒）；`consent_pending`/`denial`
  限预期响应者；首个终态响应 `markResponded`，重复响应幂等丢弃。
- 「grant 哈希用 JSON.stringify，键序不保证」→ `hashPayload` 改用 `canonicalStringify`
  （递归排序对象键、丢 undefined），登记 params_hash 与 grant payload_hash 同源。
- 「scope 大小写/空白可绕过比对」→ `normalizeScope`（trim+lowercase）在 decode、rulesEngine、
  policy.allow、checkScopeConstraints、出站登记、连接器查表全链统一。
- 「action params 无形状上限、队列无界」→ decode 层 `paramsShapeOk`：深度≤8、总键数≤128、
  数组≤200、字节≤8KB；ConsentQueue 上限 1000 条（pending≤200、单 requester≤50），满回 denial(busy)。
- 「task.run 走旧 checkRequest 绕过规则引擎」→ task 信封统一过 `decide()`：cannot 直拒；
  `legacy_allow` 白名单保留旧「允许跑任务」语义（ask+legacy 放行），其余 ask/cannot 拒。
- 「敏感 JSON 文件权限/写入方式不统一」→ `secureFile.ts`：0600 文件+0700 目录+tmp/rename 原子写，
  consents/policy/inbox/tasks/outgoing-requests/revoked 全部走它；坏 `created_at` 落 epoch 不崩启动。
- 「批准即完成的旧断言」→ `approved` 现在只是「已批准未执行」中间态，执行+回执送达才 `completed`。
