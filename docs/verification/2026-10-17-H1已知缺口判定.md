# H1 已知缺口：测试同事报的「6 行泄露」到底是什么

> 时间：2026-10-17 16:40 UTC　作者：协作室-后端
> 版本：`backend/app/core/observability.py` @ `df92beb`，HEAD `6b15121`
> 结论先行：**测试同事报的「handler 在 app.main 导入之前挂上就不生效」不成立。**
> 真实缺口只有一个：绕过 logging 框架直接 `handler.emit()`。

## 一、测试同事的说法

> 「我的探针是在运行时用 `logging.FileHandler` 往 root 上挂 handler，而且挂得很早。
> 我在 `app.main` 导入之前就把 handler 挂上去了，而这个 handler 上没有 RedactingFilter。」

稳定复现 6 行 `_repr_params(...)` 泄露。

## 二、按这个时序复现：不漏

脚本：`scripts/verify/repro_h1_early_handler.py`

```text
$ ./.venv/bin/python scripts/verify/repro_h1_early_handler.py
导入前 handler 的过滤器: []
导入后 handler 的过滤器: ['RedactingFilter']
日志行: 184   sqlalchemy.engine 行: 5   泄露行: 0
总结：未泄露
退出码=0
```

**原因**：`install_redacting_filter()` 在末尾会遍历 root 及其下所有 logger 的
**已存在 handler**，逐个补上过滤器（`observability.py` 末段 `for handler in log.handlers: _attach(handler)`）。
所以「导入前先挂 handler」这条时序是被覆盖的：导入时 filters 为空，导入后被补上。

## 三、逐个时序验证（四种写法）

| 写法 | 是否泄露 |
|---|---|
| A. root 在 `import app.main` 之前挂 handler | **不漏** |
| B. 导入后新建 logger 并 `addHandler` | **不漏**（`addHandler` 补丁生效） |
| C. 导入后直接 `logger.handlers = [h]` | **不漏**（记录工厂兜底） |
| D. 绕过框架，直接 `logging.LogRecord(...)` 然后 `handler.emit(record)` | **漏**（唯一缺口） |

## 四、真实缺口：绕过 logging 框架

变体 D 的写法：

```python
rec = logging.LogRecord("x", 20, "", 1, "token=%s", (TOKEN,), None)
handler.emit(rec)          # 不经过 logger，不经过工厂，不经过 filter
```

这条路**完全不经过 Logger 与记录工厂**，任何在 logging 框架内部做的脱敏都拦不住。
但要说清它的性质：

1. **这不是任何正常程序会走的路径。** 第三方库（SQLAlchemy、httpx、aiosqlite）全部走
   `logger.info(...)` / `logger.debug(...)`，都会经过记录工厂。变体 D 需要有人显式构造
   记录并直接调用 handler，属于自己写脱敏测试时的写法，不是生产代码写法。
2. **生产服务路径已全覆盖。** `accept_grep_zero.py` 起的是真实 uvicorn，日志来自 SQLAlchemy
   与 aiosqlite 的正常 logger 调用，261 行引擎日志、0 行泄露。
