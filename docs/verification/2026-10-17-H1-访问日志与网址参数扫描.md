# H1 修复：访问日志脱敏 + 全仓库「内容进网址」扫描

> 分支：`fix/h1-access-log`　编写：协作室-后端　日期：2026-10-17
> 复现脚本：`scripts/verify/repro_h1_access_log.py`

## 一、缺陷复现（改之前）

`GET /api/v1/invites/{token}` 的 token 是凭据（`backend/app/models/room_invite.py:12`，主键即令牌）。
uvicorn 访问日志形如 `'%s - "%s %s HTTP/%s" %d'`，路径整段进日志。

修复前的实际行为，见本文第四节「反向验证」。

## 二、修法

`backend/app/core/observability.py`：

1. 脱敏规则覆盖三类位置：
   - 路径段：`/api/v1/invites/<token>`、`/api/v1/shared/<token>`、`/api/v1/rooms/<id>/share/<token>`
   - 查询串里的凭据：`?token=` / `?access_token=` / `?api_key=` / `?secret=` 等
   - 查询串里的自由文本：`?q=` / `?query=` / `?search=`（可能是聊天正文片段）
2. **保留排查信息**（本次新增的关键一点）：原实现只要有一个参数带密钥，就把整条日志打成
   `***REDACTED***`，`GET`、路径、状态码全丢。现改为**逐个参数就地脱敏后照常渲染**：

   ```text
   修复后：127.0.0.1:5000 - "GET /api/v1/invites/***REDACTED*** HTTP/1.1" 200
   ```

   只有模板本身被改写（如 `Bearer %s`）时才退化为整条掩码，因为那时槽位结构已不可信。

根治要把令牌移到 WebSocket 首帧或子协议头，属于协议改动，须另立提案。

## 七、H1 的实际暴露面（组长要求写清：到底只是日志，还有别的口子）

### 逐层核对结果

| 环节 | 事实 | 证据 |
|---|---|---|
| 后端镜像启动 | **关掉了访问日志** | `backend/Dockerfile:23` → `--no-access-log` |
| 本机启动脚本 | 同样关闭 | `scripts/start.sh:6` → `--no-access-log` |
| 前端 nginx | **访问日志与错误日志全关**，注释写明"URI 是能力，nginx 内置格式无法脱敏" | `frontend/nginx.conf:7-8` → `access_log off; error_log /dev/null;` |
| 后端端口 | 只绑本机回环 | `docker-compose.yml:33` → `127.0.0.1:8000:8000` |
| 应用自身日志 | 不记 URL 原文 | 业务日志只记房间/用户短号 |

### 结论

**当前生产配置下，邀请链接凭据不会进任何一层日志。** 审计报告原话"生产环境真实泄露"应当下调为
"一旦打开访问日志就会泄露"。这不是我在替缺陷开脱——恰恰相反：

1. **"日志关着"不是安全边界。** 任何人为了排查问题加一个 `--access-log`、或改用 nginx 默认格式、
   或在反向代理/网关层开启日志，凭据立刻原样落地。而这些改动在运维里是常规操作，不会有人想到
   会泄露凭据。所以脱敏必须留在代码里，作为最后一道防线。**这部分已完成（已验证）。**
2. **日志不是唯一口子。** 凭据在 URL 里，还会进入：
   - 浏览器历史记录与地址栏自动补全；
   - 用户粘贴到聊天工具、工单、截图里；
   - 任何中间代理、CDN、WAF 的默认日志（这些不归本项目控制）。

   所以真正的根治，是**让凭据不再出现在 URL 里**，见下一节。

## 八、分享接口的最终地址定论（组长问的第 1 件事）

两端地址当前**确实不一致**，证据：

| 端 | 实际写法 | 位置 |
|---|---|---|
| 后端真实数据接口 | `GET /api/v1/rooms/shared/{token}/messages` | `backend/app/api/rooms.py:170`，路由前缀 `backend/app/api/rooms.py:18` |
| 前端当前请求 | `GET /api/v1/shared/{token}` | `frontend/src/pages/SharedRoomPage.tsx:19` |
| 前端页面路由（浏览器地址栏） | `/shared/{token}` | `frontend/src/App.tsx:32` |

**定论**：数据接口以**后端为准**，最终地址就是 `GET /api/v1/rooms/shared/{token}/messages`。

理由：
1. 它挂在 `rooms` 路由下，语义是"某个房间的只读分享数据"，与 `/{room_id}/share` 生成、`DELETE /{room_id}/share/{token}`
   撤销属于同一组资源，不该拆到顶层 `/api/v1/shared`。
2. `share_url` 字段返回的是 `/shared/{token}`，那是**浏览器地址栏的路由**（前端 `App.tsx` 用），不是数据接口。
   两者本来就是两个不同的东西，前端把它们混成了一个请求地址。

**前端需要改的只有一处**：`SharedRoomPage.tsx:19` 的请求地址改为
`/api/v1/rooms/shared/${encodeURIComponent(token)}/messages`，并把响应里的 `messages` 字段渲染出来。
浏览器地址栏路由 `/shared/{token}` **保持不变**，分享链接照旧能用。

## 九、加密房间仍能生成分享链接（组长问的第 2 件事）

**本分支已修**：`backend/app/api/rooms.py:138` 对 `transport == "xmtp"` 返回 409，不生成、不落库。
组长实测到 200 是因为当时那版还没这个拦截。

实测与反向验证见 `docs/verification/2026-10-17-高危修复单.md` 与
`backend/tests/test_encrypted_room_share_guard.py`：

```text
$ pytest backend/tests/test_encrypted_room_share_guard.py -q
3 passed
# 反向验证：临时删掉 409 分支 → 2 failed（明文房间那条仍通过，拦截范围正确）
```

**注意一个连带影响**：`CreateRoomRequest.transport` 只接受 `"xmtp"`（`backend/app/api/rooms.py:24`），
所以通过接口新建的房间全是加密房间，按新规则**一律不能生成分享链接**。这正是既定方向
（加密房间正文不在服务器上，没有可分享的东西），但前端如果还有"分享"按钮，会对新建房间一律收到 409，
建议直接隐藏入口或按 409 提示。已写入提交的交接口事项。
