## 交付内容

### 1. 动作参数 schema 注册表（connectors/actionSchemas.ts，新增）

- `validateActionParams(action, params)`：白名单制校验器注册表；
  schema 未登记的动作一律 `no_schema` 拒（写动作必须显式登记校验器，不裸跑任意 params）。
- `gmail.send` 校验器：`to` 必填 `string[]`（1–20 个合法邮箱）、`cc`/`bcc` 可选同形列表、
  `subject` 1–200 字符无控制字符、`body` 非空且 UTF-8 ≤ 32KiB（允许 `\t\r\n`，拒其余控制字符）、
  `account` 可选安全标识 `^[a-zA-Z0-9._-]{1,64}$`。
- 未在白名单的键（含 `from`/`headers`/`__proto__` 自有键）一律 `unknown_key:*` 拒；
  所有邮箱字段过控制字符检查，CR/LF 头部注入在入队前即拒。
- 校验 `reason` 只含字段级机械描述（进账本），不回显参数值。

### 2. Gmail 发信连接器（connectors/gmailSend.ts，新增）

- `GmailSendConnector implements Connector`，`scopes: ["gmail.send"]`；
  `execute(action, params, ctx)` 只处理规范化后的 `gmail.send`，其余 `unsupported_action`。
- 执行顺序：params 再过一遍 schema（fail closed）→ `account` 与配置的账户路由键比对 →
  读 0600 凭证文件（非 0600/缺失/JSON 畸形均 failed，不发起任何网络调用）→
  access_token 过期则先走 OAuth refresh（`refresh_token`+`client_id`+`client_secret`，注入式 fetch）→
  构 RFC822 原文（`To/Cc/Bcc/Subject/X-MAPR-Request-Id` 头，request_id 取自 `ExecuteContext`，
  不进 canonical params 哈希）→ base64url → `POST gmail.googleapis.com/gmail/v1/users/me/messages/send`。
- 结果映射：2xx+message id → `executed`（`external_id`=message id）；确定性发送前 4xx
  （400/401/403，含刷新后仍 401）→ `failed`；网络错误/超时/5xx/2xx 但无 id → `uncertain`。
  任何路径都不自动重发；401 且无法刷新 → `{status:"failed", summary:"auth_required"}`。
  日志与返回值不含 token、正文等敏感内容。

### 3. 回执结果签名绑定（grant.ts / envelope.ts）

- `envelope.ts`：`ActionResultEnvelope` 新增可选 `result_signature` 字段（decode 宽容、verify 严格）；
  `buildActionRequestEnvelope` 构造 owner 侧出站 action_request。
- `grant.ts`：`signActionResult` / `verifyActionResultSignature` 对
  `MAPR1-RESULT ` + canonical(`{grant_id, request_id, params_hash, status, receipt, summary}`) 做
  EIP-191 签名/验签——grant 签名只绑 params_hash，status/receipt/summary 由此单独绑定，
  MITM 改写任一可变字段即 `bad_result_signature`。

### 4. 执行闭环强化（consentQueue.ts / consentActions.ts / handleEnvelope.ts）

- `PendingConsent` 新增 `source?: "envelope"|"trigger"`、`account_id?: string`、
  `result_receipt`/`result_summary`（旧 consents.json 兼容加载）。
- `runApprovedAction`：params_hash 复核 → `executing`+`attempt_at` 先落盘（原子 claim，
  并发 approve 只有一个进入执行）→ `connector.execute(scope, params, {request_id, account_id})` →
  双签名回执先存 outbox 再发送；`conversation_id===""`（本机触发）跳过 XMTP 发送，状态/账本照常收口。
- connector 返回 `{status:"failed", summary:"auth_required"}` 时落终态并以
  `action_finished` + `reason:"auth_required"` 记账（沿用既有 LedgerKind，`ledger.ts` 未改）。
- `handleEnvelope` 的 `action_request` 分支在入队前跑 `validateActionParams`，
  失败回 `denial(out_of_scope)` 且账本记 `invalid_params:<reason>`；
  `action_result` 分支在出站登记匹配 + grant 验签之后追加 `verifyActionResultSignature`。

### 5. 主人审批台（ownerConsole.ts / ownerConsoleHtml.ts / index.ts）

- `GET /api/state` 返回的 consent 一律脱敏：去掉 `params`/`outbox`，代以 `params_meta`
  （键清单 + 截断预览；`body/content/text` 等正文字段只给 `[N 字符]` 长度，不透内容）。
- 新增 `GET /api/consents/{id}`：loopback + `X-MAPR-Owner` 头才返回完整 params/outbox/结果字段。
- 新增 `POST /api/action-requests`：owner 头发起出站 action_request；
  `index.ts` 中先 `buildActionRequestEnvelope` + 本地 schema 校验，再在 `outgoingRequests`
  落盘登记（kind:"action" + params_hash + action TTL），**先登记后发送**（R0 不变量），发送后记 `request_sent`。
- 审批页：发起动作请求表单；action 卡渲染收件人/cc/bcc/账户/主题/正文与 rule_hit、
  expires_at、执行状态、receipt；pending 有 Approve/Deny，`awaiting_receipt` 有 Resend Receipt；
  `uncertain` 显示「结果不明，请人工对账，不要重复执行」警示。全部经 `textContent` 渲染，不拼不可信 HTML。
- `index.ts` 在 `gmail.json` 凭证存在时同时注册 `GmailReceiptConnector` 与 `GmailSendConnector`。

## 遗留问题

- 真实 Gmail API 与真实 XMTP 群链路未验证；需另开验收并获人类批准后才可触网。
- `result_signature` 在 decode 层保持可选（向后兼容），但 verify 层缺失即拒；
  旧版对端发出的无签名回执将被 `bad_result_signature` 拒绝——属预期收紧。
- OAuth refresh 成功后更新的 token 目前只存在内存中，未回写凭证文件（凭证文件仍 0600 只读语义）。
- owner console 详情端点与动作请求端点仅在 loopback + `X-MAPR-Owner` 下开放，与既有 owner 操作同一防线。
