### 2.1 全量失败几条、按文件归类

**干净 sqlite + 真 Redis（6399）**
- 结果（`pytest backend/tests`，干净库 + 6399 Redis）：**690 通过 / 84 跳过 / 6 失败**。
  - 其中 5 条是 Redis 端口在跑的过程中掉线（`PONG` 之后测试中途再连接被拒），属环境类。
  - 剩下 1 条是真失败：`test_postgresql_offline_ddl_and_revision_head`。
- **CI 同款命令**（`pytest backend/tests tests`，干净库 + 6399 Redis，即 `audit-round4-ci.yml:180` 那一条）：**740 通过 / 80 跳过 / 1 失败**。

  - 注意：这条命令用的是 sqlite，PG 专属门禁按设计 skip，所以 hub 那 30 个失败在这条命令里不会出现。CI 上用真 PostgreSQL，H2 会在那边复现。

### 2.3 H2 根因：`tests/e2e_real_cli_test.py` 第 20 行

```python
# tests/e2e_real_cli_test.py 模块级，pytest 只要“收集到”这个文件就会执行
os.environ["MAPR_DATABASE_URL"] = f"sqlite+aiosqlite:///{PROJECT_ROOT}/e2e_cli_test.db"
```

这条赋值在模块级，**这个文件没有任何测试用例（`no tests collected`）也会执行**。之后 hub 子进程用 `env = os.environ.copy()`（`backend/tests/test_pg_room_hubs_linux.py:86`）继承了这个 sqlite 地址，子进程读不到真实 PG 里的用户和房间，WebSocket 握手返回 403。`tests/run_e2e.py` 第 15 行有同样的写法。

对照组（同一台机器、同一个库）：

| 跑法 | 结果 |
|---|---|
| `pytest backend/tests/test_pg_room_hubs_linux.py` | 17 通过 |
| `pytest tests/test_deploy_script.py backend/tests/test_pg_room_hubs_linux.py` | 22 通过 |
| `pytest tests/e2e_real_cli_test.py backend/tests/test_pg_room_hubs_linux.py` | 17 失败（61.9 秒，与单独跑 80 秒以下量级不同，说明是数据源被换掉，不是变慢） |
| `pytest backend/tests/test_pg_room_hubs_linux.py`（紧接上一组再跑一次） | 17 通过（80.1 秒） |
| `pytest backend/tests tests` | 大范围失败 |

所以后端修复单里“先加 4003 诊断、再改 `sys.path`、再加子进程环境白名单”那一套**不需要**；把两处模块级赋值挪进函数或用 `monkeypatch` 就够了。白名单那一步可以作为加固保留，但不是本次必需。

## 4. 与此清单直接相关的两个结论（给用户决定用）

1. **“30 个失败”不是代码坏了，是本机跑法被 `tests/` 里的环境变量污染**。干净环境下全量 0 失败。
2. **H3 的迁移一旦进主干而不改 `EXPECTED_ALEMBIC_HEAD`，`/ready` 健康检查和这条门禁用例会一起失败**。三处必须同一次提交。
