**给谁看**：给用户看"我们要做什么、会看到什么结果"。
**谁执行**：我们。**用户不需要敲任何命令、不需要连数据库、不需要点任何按钮。**
**日期**：2026-10-17（第三版：删掉了所有让用户执行的步骤，并修掉查重口径不一致）
**负责文档**：协作室-文档。**负责执行**：协作室-智能体（脚本与迁移）、协作室-组长（生产机权限）、协作室-测试（复跑验收）。

## 0. 这件事是什么

### 修的是什么毛病

现在系统里，`张三_老板` 和 `张三-老板` 会被当成两个人，可以各注册一个账号。
结果就是"同一个人用两种写法"混进系统，后面分不清谁是谁。

我们要在数据库里加一道唯一约束，让系统从根上不允许这种重复。

### 你需要做什么

**什么都不用做。** 全程由我们执行，事后把原样结果贴给你看。

### 唯一需要你点头的一件事

改生产库的表结构属于项目规矩里的高风险操作。
所以流程是：**我们先只读查一遍，把结果给你看，你点头，我们再改。**

---

## 1. 我们会做什么（三步）

### 第 1 步：只读查重

**在哪做**：生产服务器上，数据库容器内部。
**怎么保证只读**：进门第一件事就是把会话设成"只读"。设完之后，任何写语句都会被数据库直接拒绝。

**用哪个脚本**：`scripts/verify/prod_readonly_duplicates.sh`。
它只做三件事：读出账号名单、按"是不是同一个人"分组、打印有几组重复。
**不执行迁移、不改表、不删账号、不打印密码。**

**有一点必须先修好再用**：这个脚本原来判断"是不是同一个人"用的是 SQL 里的简单写法，
和真正改表用的判断标准不一致。全角 `Ａlice` 和 `alice` 这两类名字，脚本会当成两个人。
所以第 1 步必须先把判断标准统一到同一份代码上，否则查出来的"0 组"不能信。见第 3 节。

**你会看到什么**：一个数字——**有几组重复**。群里只报这个数字。

### 第 2 步：把结果给你看，等你点头

**如果结果是 0 组**：说明可以直接加约束。我们把结论给你，等你批准。
**如果结果大于 0 组**：我们不删号、不改号，先给你一份处置选项（见第 4 节），由你定。

### 第 3 步：你点头之后，加唯一约束

**在哪做**：生产服务器上，后端容器内部，执行项目里标准的改表工具。

**具体改什么**：
- 给账号表加一列 `comparison_username`，存"是不是同一个人"的判断依据；
- 在这一列上加唯一索引。

**不会做的事**：
- 不删任何账号；
- 不改任何已有账号的名字；
- 不动原来那一列，登录还在用它。

**如果真撞上重复**：迁移会在建索引之前自己停下来，整件事回滚。
表结构不留半成品、账号一个不少、版本号也不前进。这一点在测试库上实测过。

## 2. 我们会怎么告诉你结果

每一步做完，贴三样东西：

1. 做了哪一步，在哪台机器、哪个容器里做的；
2. **原始输出**——不是"成功"两个字，是屏幕上真实打出来的内容；
3. 这一步有没有改数据，改了什么。

两个关键数字：
- 查重结果：有几组重复；
- 迁移结果：有没有出现 `Running upgrade h80c20261015 -> i90c20261017` 这一行。

**群里只报"有几组"这个数字**，不贴打码后的名字清单。名字再短也是别人的账号信息。
要看具体是哪几个账号，由组长单独确认。

## 3. 查重口径必须先统一（这是硬前置条件）

**现状**：现在有三份"是不是同一个人"的判断逻辑——应用层、查重脚本、迁移脚本。
应用层用的是 `backend/app/agent/identity.py` 的 `comparison_identity`，迁移里抄了一份一样的。
查重脚本用的是 SQL 里另写的一段，**少做了全角转半角这一步**。

实测出来的差异：

| 两个名字 | 应用层和迁移判定 | 现在的查重脚本判定 | 后果 |
|---|---|---|---|
| `Ａlice`（全角 A）和 `alice` | 同一个人 | 两个不同的人 | 查重报 0 组，迁移却撞上 1 组 |
| `abc` 末尾带制表符和 `abc` | 同一个人 | 两个不同的人 | 同上 |

**最坏的情况**：查重说"没事"，你点了头，迁移却因为撞到重复而停下。
迁移会安全回滚、不删号，但会白跑一趟，还会让你以为出了错。

**怎么改（推荐，改动最小）**：
查重改为调用迁移里那一份 Python 比较函数，SQL 只负责把账号名读出来。
这样三处永远用同一个函数，不会再各自漂移。

**验收**：用同一对重复账号分别跑应用层、查重、迁移，三者结论必须完全一致。
**这一条做完之前，第 1 步的"0 组"不能当作加约束的依据。**

## 4. 如果查出来有重复账号，怎么处置

**先说清楚：没有任何一个选项是"自动删号"。** 脚本和迁移都不会删号，这是刻意的。

处置由你选：

### 选项 1：先查清楚（建议先做）

弄清这些账号背后是不是真的同一个人。可能只是同名，也可能是同一个人注册了两次。
**没弄清楚之前什么都不动。**

### 选项 2：保留一个、停用其余（最推荐）

确认是同一个人后：保留现在还在用的那个，把其余账号停用。
停用就是把账号的 `is_active` 改成 `false`，账号还在、数据不丢，随时能恢复。

### 选项 3：保留一个、改名其余

想全都留着：把其余账号改成明确不冲突的名字。改完要继续核对，别改出新冲突。

### 选项 4：删号

**我们不会走这条。** 选项 2 已经能达到目的，而且可逆。删号不可逆，不值得冒这个险。

## 5. 有两件事和本手册相关

### 5.1 第 1 步怎么在生产机上跑，组长还在解决跑法

组长做了一个只读检查任务，想在 GitHub 上手动触发，跑在生产服务器那台机器上。
碰到了限制：**新加的流程文件只有放在主分支上才会被识别**，放在别的分支触发一律返回"找不到"。

组长没有为了让它在分支上跑起来去动主分支。**这一条不影响你，也不影响我们手动执行。**

因为你要的是"技术活全归我们"，所以就算那个任务暂时跑不了，第 1 步也可以由我们在生产服务器上直接跑同一个脚本。
两条路的区别只有一条要说清：**手动跑的时候，"只读"靠的是脚本里的只读设置，不靠那个任务的保险装置**，所以执行的人要多核一次。

### 5.2 第 3 步之前要先改一处版本号

改完表结构后，代码里记的"数据库版本号"要跟着改，不然健康检查会以为数据库版本不对。
这一处**刻意还没改**——现在改了，健康检查会和真实库对不上，比现在更糟。

## 6. 撤回的办法

如果加完约束后发现它挡住了你认为正常的情况，可以退回去。

**怎么退**：在生产服务器上执行回退命令，把新加的那一列和约束去掉，版本号退回上一版。
**账号一个都不会少**——在测试库上实测过：撤回后账号数量不变。

这一步同样由我们做。

## 8. 边界

1. 唯一约束只保证数据库这一层，不能替代应用层的判重。两者都要有。
   应用层判重已在提交 `0d8d5c9` 修好（标点变体视为同一个人），这次是把第二道防线补齐。
2. **迁移脚本已经写好，但一行都没在生产库上执行过。**
3. 生产库的操作只由我们执行，**执行前必须让你看到只读查重的结果并点头**。
4. 执行过程中如果遇到和本手册写的不一样的情况，**停下来报告，不猜、不将就着往下走**。
