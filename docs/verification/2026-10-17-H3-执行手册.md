# H3 执行手册：给账号加唯一约束，防止标点变体重复注册

写给了谁：给用户本人（不是技术人员）照着做的步骤。
执行人：只由用户本人执行。
日期：2026-10-17

---

## 0. 先说清三件事

**这件事为什么要做？**

现在系统里，`张三_老板` 和 `张三-老板` 会被当成两个人，可以各注册一个账号。
这会让"同一个人用两种写法"混进系统，后续分不清谁是谁。
加一道数据库层面的唯一约束，就是让系统从根上不允许这种重复。

**要动数据库，所以必须由你本人执行。** 智能体只写好了脚本，没有碰生产库。

**一共三个脚本，各管一件事：**

| 文件 | 做什么 | 会不会改数据 |
|---|---|---|
| `scripts/verification/h3_check_duplicates_readonly.py` | 查有没有重复账号 | **只看，不改** |
| `backend/alembic/versions/i90c20261017_add_unique_comparison_username.py` | 加唯一约束 | 会改表结构，**不删账号** |
| 本文件 | 告诉你按什么顺序做 | — |

---

## 1. 第一步：查重（只读）

**做什么**：看看生产库里现在有没有"同一个人的两种写法"。

**怎么跑**（二选一）：

**做法 A —— 只打印 SQL，手动在数据库控制台执行**

```text
python scripts/verification/h3_check_duplicates_readonly.py --sql-only
```

它会打印一条查询语句。把这条语句粘贴到数据库管理界面里执行。
这种做法最稳妥，因为你自己能看见 SQL 内容。

**做法 B —— 给脚本一个只读连接串，让脚本自己查**

```text
python scripts/verification/h3_check_duplicates_readonly.py --dsn "你的只读连接串"
```

脚本自己会开一个"只读会话"，数据库会直接拒绝任何写入。这一点我在这台机器上实测过：写入被数据库拒绝。

**你会看到什么**

正常情况（没有重复）：

```text
扫描到账号总数        : 128
判为同一个人的组数    : 128
存在重复的组数        : 0

结论：没有发现重复账号。可以继续执行加唯一约束的迁移。
```

（上面数字是举例，你的实际数字会不一样。）

有问题（有重复）：

```text
存在重复的组数        : 1

结论：发现重复账号。**必须先处置，不能直接加唯一约束。**

组 [zhangsan-owner] 共 2 个账号：
    zh**********er           注册时间 2026-09-01 10:00:00+00:00
    zh**********er           注册时间 2026-09-20 10:00:00+00:00
```

**注意：名字是打码的**，只留前后各 2 个字。这是故意的——排查是必要的，导出完整账号清单不必要。
如果你需要看清具体是哪几个账号，请自己在数据库界面里查。
请只在群里报"有几组"这个数字，不要把打码后的名字清单贴出来——名字再短也是别人的账号信息。


**什么时候必须停**

| 你看到 | 怎么办 |
|---|---|
| `存在重复的组数 : 0` | 继续做第 2 步 |
| `存在重复的组数` 大于 0 | **停。** 先按第 4 节处置，处置完再回来重跑第 1 步 |
| 连不上数据库 | 停。把报错类型告诉我，不要自己改连接串乱试 |

## 2. 第二步：先备份

**做什么**：把现在的账号表备份一份。

**为什么**：加约束是改表结构。虽然脚本已经做到"出错就整体回滚"，但备份是最便宜的安全网。

**怎么做**：用你平时的备份办法即可。最小要求是**只备份 `users` 这一张表**。例如：

```text
pg_dump --data-only --table=users 你的库名 > users_backup_20261017.sql
```

**看到什么算正常**：生成的文件不是 0 字节。

**什么时候必须停**：备份失败或文件为 0 字节，就不要做第 3 步。

---

## 3. 第三步：加唯一约束

**做什么**：执行迁移脚本，给 `users` 表加一列"比较键"并在这列上加唯一约束。

**怎么跑**：

```text
cd backend
alembic upgrade head
```

（`alembic` 是本项目用来改表结构的工具，`upgrade head` 意为"升到最新版本"。）

**你会看到什么**

正常：

```text
INFO  [alembic.runtime.migration] Running upgrade h80c20261015 -> i90c20261017, add unique constraint on users.comparison_username (H3)
```

看到这一行、且没有红色报错，就是成功了。

**如果报错说"存在被判为同一个人的重复账号"**

```text
RuntimeError: users 表里存在被判为同一个人的重复账号，已在建唯一索引之前停止。冲突组数=1...
```

这说明第 1 步之后、这一步之前，又冒出了重复账号（例如正好有人在注册）。
**这是保护机制在工作，不是失败。** 脚本已经在出错时整体回滚：
表结构没有半成品、账号一个没少、版本号也没前进。

处置办法：回到第 1 步重跑查重，按第 4 节处理，再回来做这一步。

**做什么验证成功了**

回到第 1 步的方法，再看一次：

```text
存在重复的组数        : 0
```

并且可以顺手确认约束确实生效了（下面这条是只读查询）：

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'users' AND indexname = 'ux_users_comparison_username';
```

应该看到一行，`indexdef` 里有 `CREATE UNIQUE INDEX`，也就是带 `UNIQUE` 字样。

**什么时候必须停**：任何情况下都不要自己删账号去"凑"出一个干净的库。

## 4. 查到重复账号时，怎么办

**先明确：没有任何一个选项是"自动删号"。** 脚本和迁移都不会删号，这是刻意的。

下面是处置选项，由你选：

**选项 1：什么都不做，先查清楚（推荐先做这一步）**

先弄清这些账号背后是不是真的同一个人。可能只是同名，也可能是同一个人注册了两次。
**没弄清楚之前不要动手。**

**选项 2：保留一个、停用其余**

如果确认是同一个人：保留现在还在用的那个，把其余账号设为"停用"（把 `is_active` 改成 false）。
**不删数据**，随时可恢复。这是最稳的做法。

**选项 3：保留一个、改名其余**

如果确认是同一个人，但想全都留着：把其余账号改名成明确不冲突的名字（例如 `zhangsan_owner_old`）。
注意：改名之后要继续核对，别改出新冲突。

**选项 4：删号**

只有在你完全确认、并且已经做好备份时才可以考虑。
**建议在任何情况下都不要走这一条**，选项 2 已经能达到目的，而且可逆。

选完之后，重跑第 1 步确认变成 0 组，再做第 3 步。

## 5. 万一要撤回（回滚）

**什么时候用**：加完约束后，发现它挡住了你认为正常的情况，要退回去。

**怎么做**：

```text
cd backend
alembic downgrade h80c20261015
```

**你会看到什么**：

```text
INFO  [alembic.runtime.migration] Running downgrade i90c20261017 -> h80c20261015, ...
```

**撤回后是什么状态**：新加的那一列和那个约束都没了，版本号退回上一版。
**账号一个都不会少**——我在这台机器上实测过：撤回后账号数量不变。

## 7. 一条需要认清的边界

本手册里的"唯一约束"只保证**数据库层不再重复**。

它**不能**替代应用层的判重逻辑。两者都要有：
应用层判重负责"友好地返回 409 给用户"，数据库约束负责"并发时也绝不重复"。

应用层判重已在提交 `0d8d5c9` 修好（标点变体视为同一个人）。
本迁移是把第二道防线补齐。
