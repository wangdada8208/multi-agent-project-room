# H3 执行手册：给账号加唯一约束，防止标点变体重复注册

**给谁看**：给用户本人（不是技术人员）照着做的步骤。
**谁来执行**：只由你本人执行。
**日期**：2026-10-17

## 0. 动手前先读这一段

### 这件事为什么要做

现在系统里，`张三_老板` 和 `张三-老板` 会被当成两个人，可以各注册一个账号。
结果就是"同一个人用两种写法"混进系统，后面分不清谁是谁。

加一道数据库层面的唯一约束，就是从根上不允许这种重复。

**这是改数据库结构，所以必须由你本人执行。** 我们已经写好脚本，没有碰生产库。

### 三个文件各管一件事

| 文件 | 做什么 | 会不会改数据 |
|---|---|---|
| `scripts/verification/h3_check_duplicates_readonly.py` | 查有没有重复账号 | **只看，不改** |
| `backend/alembic/versions/i90c20261017_add_unique_comparison_username.py` | 加唯一约束 | 改表结构，**不删账号** |
| 本文件 | 告诉你按什么顺序做 | — |

### 术语对照表（看着像外语的词，这里都有白话）

### 全程最重要的三条

1. **每一步都要先看"正常输出"再往下走。** 对不上就停，别猜。
2. **任何一步看到红色报错就停。** 停下来，把报错类型告诉组长，不要自己改连接串试。
3. **绝对不要为了凑一个干净的库去删账号。** 下面的备份和处置方案已经够用了。

## 第 1 步：查有没有重复账号（只看，不改）

### 在哪个目录

打开终端，先进入**项目根目录**（也就是有 `alembic.ini` 和 `scripts/` 这个文件夹的那一层）。

```text
cd 你的项目根目录
```

**怎么确认进对了**：敲下面这条，能看到 `alembic.ini` 就在结果里。

```text
ls
```

### 敲什么

**做法 A（推荐，最稳妥）：只打印 SQL，你自己在数据库界面里执行**

```text
python scripts/verification/h3_check_duplicates_readonly.py --sql-only
```

它会把一条查询语句打在屏幕上。复制这条语句，粘贴到你的数据库管理界面里执行。
好处是：**你能亲眼看见它到底查了什么**，脚本没机会乱来。

**做法 B：给脚本一个只读连接串，让脚本自己去查**

```text
python scripts/verification/h3_check_duplicates_readonly.py --dsn "你的只读连接串"
```

脚本会自己开一个"只读会话"，数据库会直接拒绝任何写入。
这一点我在这台机器上实测过：写入被数据库拒绝。

### 正常输出长什么样

没有重复（可以继续）：

```text
==============================================================
H3 查重结果（只读，未修改任何数据）
==============================================================
扫描到账号总数        : 128
判为同一个人的组数    : 128
存在重复的组数        : 0

结论：没有发现重复账号。可以继续执行加唯一约束的迁移。
```

**要看的就一个数：`存在重复的组数`。**
它是 `0`，才继续下一步。数字是举例，你的实际数字会不一样。

有重复：

```text
存在重复的组数        : 1

结论：发现重复账号。**必须先处置，不能直接加唯一约束。**

组 [zhangsan-owner] 共 2 个账号：
    zh**********er           注册时间 2026-09-01 10:00:00+00:00
    zh**********er           注册时间 2026-09-20 10:00:00+00:00
```

### 关于名字被打码

名字只留前后各 2 个字，中间都是星号。这是故意的：排查是必要的，导出完整账号清单不必要。
需要看清具体是哪几个账号，请自己在数据库界面里查。

**在群里只报"有几组"这个数字**，不要把打码后的名字清单贴出来。名字再短也是别人的账号信息。
**更不要把连接串贴进群里**，里面有密码。

### 看到什么必须停

| 你看到 | 含义 | 怎么办 |
|---|---|---|
| `存在重复的组数 : 0` | 没问题 | 继续做第 2 步 |
| `存在重复的组数` 是 1 或更大 | 有重复 | **停。** 按第 4 节处置，处置完回来重跑本步 |
| `连接或查询失败：ConnectionRefusedError` 之类 | 连不上数据库 | **停。** 把括号里那个英文错误类型告诉组长 |
| `缺少 --dsn 或 MAPR_READONLY_DSN` | 没给连接串 | 用做法 A，或者补上 `--dsn` |

## 第 2 步：先备份（强烈建议，不要跳过）

### 在哪个目录

终端打开在哪都行，但备份出来的文件会存在你当前所在的位置。
建议还在项目根目录，方便找。

### 敲什么

```text
pg_dump --data-only --table=users --host=数据库地址 --port=端口 --username=用户名 --dbname=库名 > users_backup_20261017.sql
```

**看不懂就把这条填一下**：把 `数据库地址`、`端口`、`用户名`、`库名` 换成你实际的。
执行时它会问一次数据库密码，输进去就行。

如果你平时有现成的备份流程，也可以直接用它。**最低要求：`users` 这张表被备份了。**

### 正常输出长什么样

`pg_dump` 成功时**屏幕上什么都不打印**，这是正常的。

### 怎么确认备份成功

```text
ls -l users_backup_20261017.sql
```

看文件大小，**明显大于 0 就行**。

### 看到什么必须停

| 你看到 | 怎么办 |
|---|---|
| 文件不存在 | **停。** 备份没成功，不要做第 3 步 |
| 文件是 0 字节 | **停。** 同上 |
| `password authentication failed` | **停。** 密码或账号不对，告诉组长 |

## 第 3 步：加唯一约束

### 在哪个目录

**必须在项目根目录**（有 `alembic.ini` 的那一层）。**不要进 `backend` 文件夹。**
进错了会报"找不到配置文件"。

```text
cd 你的项目根目录
```

### 先做一件事：确认迁移连的是哪个数据库

**这一步不能省。** 迁移只认环境变量 `MAPR_DATABASE_URL`。
如果没设，它会悄悄去连一个示例地址（`localhost:5432`），你会以为迁移成功了，其实改的是别处。

查一下现在设的是什么：

```text
echo $MAPR_DATABASE_URL
```

- 如果**打印出你的生产库连接串**：对了，继续。
- 如果**打印一行空白**：说明没设。请先按你的部署方式设好，例如：

```text
export MAPR_DATABASE_URL="你的生产库连接串"
```

（Windows PowerShell 用 `$env:MAPR_DATABASE_URL="..."`。）

设完再 `echo` 一次确认。

### 敲什么

```text
alembic upgrade head
```

`upgrade head` 的意思是"升到最新版本"。

### 正常输出长什么样

```text
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade h80c20261015 -> i90c20261017, add unique constraint on users.comparison_username (H3)
```

**关键是要看到最后那一行 `Running upgrade ... -> i90c20261017`。** 看到它、且没有红色报错，就是成功了。

### 如果报错说"存在被判为同一个人的重复账号"

```text
RuntimeError: users 表里存在被判为同一个人的重复账号，已在建唯一索引之前停止。冲突组数=1...
```

**这是保护机制在工作，不是失败。**
说明第 1 步之后、这一步之前又冒出了重复账号（例如正好有人在注册）。

迁移已经在出错时整体回滚：**表结构没有半成品、账号一个没少、版本号也没前进。**
这一点我在这台机器上造了重复库实测过。

处置办法：回到第 1 步重跑查重，按第 4 节处理，再回来做这一步。

### 如果报错是连不上数据库

看到 `ConnectionRefusedError` 或 `password authentication failed`：**停。**
回到上面"确认迁移连的是哪个数据库"那一节，先确认连接串对不对。

### 怎么做成功验证

一、重跑第 1 步，`存在重复的组数` 应该是 `0`。

二、在数据库界面里执行下面这条只读查询，确认约束真的建上了：

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'users' AND indexname = 'ux_users_comparison_username';
```

应该看到**一行**，且 `indexdef` 里带 `CREATE UNIQUE INDEX`（关键是 `UNIQUE` 这个词）。
一条都没查到，说明迁移没作用在你以为的那个库上，回到"确认迁移连的是哪个数据库"。

### 看到什么必须停

- 没看到 `Running upgrade ... -> i90c20261017` 那一行
- 看到红色报错但不是"重复账号"那一种
- 第 3 步做完，上面那条查询却查不到索引

三种情况都**停**，把屏幕输出交给组长。**不要自己重复执行迁移。**

## 第 4 步：查到重复账号时怎么办

**先说清：没有任何一个选项是"自动删号"。**
脚本和迁移都不会删号，这是刻意的。

下面几个选项由你选：

### 选项 1：先查清楚（建议先做这个）

弄清这些账号背后是不是真的同一个人。可能只是同名，也可能是同一个人注册了两次。
**没弄清楚之前不要动手。**

### 选项 2：保留一个、停用其余（最推荐）

确认是同一个人后：保留现在还在用的那个，把其余账号"停用"。
停用就是把这个账号的 `is_active` 字段改成 `false`，账号还在、数据不丢，随时能恢复。

### 选项 3：保留一个、改名其余

想全都留着：把其余账号改成明确不冲突的名字（例如 `zhangsan_owner_old`）。
注意改完要继续核对，别改出新冲突。

### 选项 4：删号

只有在你完全确认、并且已经做好备份时才考虑。
**建议任何情况下都不要走这条**，选项 2 已经能达到目的，而且可逆。

选完之后，重跑第 1 步，确认变成 0 组，再做第 3 步。

## 第 5 步：万一要撤回（回滚）

### 什么时候用

加完约束后，发现它挡住了你认为正常的情况，要退回去。

### 在哪个目录

和迁移一样：**项目根目录**，并且同样要先确认 `MAPR_DATABASE_URL` 指向你要改的那个库。

### 敲什么

```text
alembic downgrade h80c20261015
```

### 正常输出长什么样

```text
INFO  [alembic.runtime.migration] Running downgrade i90c20261017 -> h80c20261015, add unique constraint on users.comparison_username (H3)
```

### 撤回后是什么状态

新加的那一列和那个约束都没了，版本号退回上一版。

**账号一个都不会少。** 我在这台机器上实测过：撤回后账号数量不变。

### 怎么确认撤干净了

```sql
SELECT indexname FROM pg_indexes
WHERE tablename = 'users' AND indexname = 'ux_users_comparison_username';
```

应该**查不到任何行**。

## 第 6 步：做完之后，请告诉组长这三件事

1. 第 1 步的 `存在重复的组数` 是多少。
2. 第 3 步有没有看到 `Running upgrade ... -> i90c20261017`。
3. 有没有走第 4 步处置（有的话，选的是哪个选项）。

**这三个数请如实报，不要美化。** 有重复是正常情况，处置掉就好。

## 附二：一条需要认清的边界

本手册里的唯一约束，只保证**数据库这一层不再重复**。

它不能替代应用层的判重逻辑，两者都要有：
- 应用层判重负责"友好地告诉用户这个名字已被占用"；
- 数据库约束负责"两个人同时提交时，也绝不出两个账号"。

应用层判重已在提交 `0d8d5c9` 修好（标点变体视为同一个人）。
这次迁移是把第二道防线补齐。
