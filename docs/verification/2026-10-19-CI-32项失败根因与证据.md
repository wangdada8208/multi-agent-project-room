# CI 32 项后端失败：根因与证据（2026-10-19）

> 结论先行：**32 项失败不是 32 个缺陷，而是 3 个原因**。
> 其中 **25 项**共用一个根因（测试的 DNS stub 挟持了数据库连接），
> **5 项**是因为 Deploy 的 test job 根本没有 Redis 服务，
> 只有 **2 项**是真实的 H3 产品缺陷。

---

## 0. 先纠正两个前提

1. **用户引用的 `Run #39122831109` 不是第四轮审计 CI，而是 `Deploy` 工作流。**
   通过公开 GitHub API 核实：`name: "Deploy"`、`path: .github/workflows/deploy.yml`、
   `event: push`、`head_branch: main`、`head_sha: 08f3ae3`。
   它的 job 结构是 `test`=failure、`build`=skipped、`deploy`=skipped，
   失败的步骤精确是 **`Run tests`**，而 **`Run migrations` 是 success**。
   所以"build 与 deploy 均被跳过"是 Deploy 工作流内部 `needs: test` 的正常结果，
   不是审计 CI 的行为。

2. **审计 CI（audit-round4-ci.yml）确实也在失败，而且与 Deploy 是同一个根因。**
   Run `39030900848`、`39028768688` 等，都是
   `Backend (real PostgreSQL + real Redis + Alembic)` job 的
   `Full backend + integration test suite` 步骤失败，其余 job（frontend / hygiene / safety-guard）全绿。

3. PR #5 核实：`merged: true`、`merged_at: 2026-10-18T11:20:22Z`、base `main`、
   head `integration/audit-round4`。Run #39122831109 创建于 `11:20:24Z`，
   即**合并后 2 秒**由这次 push 触发。

## 3. 根因一：25 项 = 测试的 `socket.getaddrinfo` stub 挟持了 PostgreSQL 连接

### 3.1 机制

1. CI 两个工作流的 DSN 都用主机名 **`localhost`**（日志原文，env 已被 GitHub 打码保留尾部）：
   `MAPR_TEST_DATABASE_URL: ***localhost:5432/agent_room_test`
2. 失败的那批测试都 monkeypatch 了 `socket.getaddrinfo`，且**对任意 host 都返回同一个合成公网 IP**：
   - `backend/tests/test_a2a_egress_ssrf_linux.py:53`（`network` fixture 的 `dns()`）、`:272`
   - `backend/tests/test_agent_url_ssrf_linux.py:94 / :109 / :153 / :183 ...`
   - `backend/tests/test_a2a_protocol_v1_linux.py:386`（interop 用例）
   形如 `return [(socket.AF_INET, socket.SOCK_STREAM, 6, "", (state.ip, port))]`，**不区分 host**。
3. asyncpg 连数据库时，host 是 `localhost` → 不是数字字面量
   → asyncio **不会**走 `_ipaddr_info` 快路径 → 调用被 patch 过的 `socket.getaddrinfo`
   → 拿到合成 IP `93.184.215.14` → 去连 `93.184.215.14:5432`（黑洞地址）
   → **asyncpg 默认 60 秒连接超时 → `asyncio.TimeoutError`**。
4. 真实日志的 traceback 与此完全吻合：
   `asyncpg/connection.py:2497 in connect` → `async with compat.timeout(timeout)`
   → `asyncio/timeouts.py:117 raise TimeoutError from exc_val` → `E TimeoutError`。

### 3.2 决定性实验（本机复现）

同一个用例，**只改 DSN 的主机写法**，其余完全不变：

| DSN 主机 | 结果 |
| --- | --- |
| `127.0.0.1`（数字 IP） | `1 passed in 0.49s` |
| `localhost`（主机名） | `1 failed in 60.98s`，`E TimeoutError` |

`127.0.0.1` 是数字 IP，asyncio 走 `_ipaddr_info` 快路径**完全不调用 `getaddrinfo`**，
所以无论 DNS stub 怎么写都测不出这个问题——这就是缺陷能存活至今、
以及"本机全绿、CI 全红"的全部原因。

### 3.3 这一条同时解释了 A2A 互操作那 1 项

`test_a2a_protocol_v1_linux.py::test_client_server_standard_interoperation_without_network`
断言 `task['status'] == 'submitted'`，CI 得到 `failed`。
该用例同样 patch 了 `getaddrinfo`，`send_task` 落库时 PG 连接超时抛异常，
被 `backend/app/a2a/server.py:649-650` 的 `except Exception` 兜成
`{"status": "failed", "result": [{"text": "Task submission failed"}]}`，
且 `logger.warning("task submission failed; details suppressed")` **吞掉了原始异常**。

**因此它不是真实缺陷，而是根因一的下游表现。** 断言本身是对的，不需要改。

## 4. 根因二：5 项 = Deploy 的 test job 没有 Redis 服务

`deploy.yml` 的 `test` job 原本**只有一个 postgres service，完全没有 redis service**，
且 `Run tests` 步骤只设 `MAPR_TEST_DATABASE_URL` / `MAPR_DATABASE_URL` / `PYTHONPATH`，
**没有 `MAPR_TESTING`，也没有 `MAPR_TEST_REDIS_URL`**。

代码依据：`backend/app/auth/rate_limit.py:129` 只要 `MAPR_TEST_DATABASE_URL` 存在就判定为测试环境；
`_get_effective_redis_url()`（`:138-149`）在未设 `MAPR_TEST_REDIS_URL` 时回退到
`settings.redis_url`（默认 `redis://localhost:6379/0`）并改写为 DB 15
→ **`localhost:6379` 连接被拒绝**，与日志原文
`Error 111 connecting to localhost:6379. Connection refused.` 完全一致。
Redis 不可用时 `_get_redis_sync()` 返回 `None`，
于是依赖真实 Redis 的用例报 `AttributeError: 'NoneType' object has no attribute 'scan_iter'`。

对照：`audit-round4-ci.yml` 的 backend job **有** redis:7-alpine service，
并在 job 级设了 `MAPR_TESTING=1` 与 `MAPR_TEST_REDIS_URL`，
还有一步"Prove real PostgreSQL and real Redis are wired (no silent skip)"。

## 5. 根因三：只有 2 项是真实 H3 产品缺陷

`test_register_race_linux.py`：

- `test_concurrent_registration_creates_exactly_one_account[_x_bot-_x-bot]`
  → `expected one 200 and one 409, got [200, 200]`：**真实并发缺陷**（检-插窗口）。
- `test_normalized_username_has_unique_index`
  → 断言 `normalized_username` 上有唯一索引，而设计上唯一索引建在 `comparison_username` 上。

**本机单独运行这 2 项同样失败**，说明它们与 CI 环境无关，是真实问题。
（第 2 项是断言与设计不一致，需要按设计改为验证 `ux_users_comparison_username`。）

## 6. 结论：哪些不是缺陷

- **SSRF 防护逻辑没有失败**：24 项 `TimeoutError` 全部是连接数据库超时，
  与 URL 校验、私网拦截、DNS pinning 的正确性无关。
- **Redis 限流产品逻辑没有失败**：5 项全部是"没有 Redis 可连"，
  不是限流算法或脱敏逻辑错误。
- **A2A 互操作协议实现没有失败**：那 1 项是被数据库超时连累的下游表现。

这与用户"这些不能直接判定为 SSRF 漏洞或 Redis 产品逻辑错误"的判断一致，
但现在可以更进一步：**它们有明确的、可复现的环境根因，而不是"测试隔离仍有问题"这种笼统描述。**

## 7. 已实施的修复

### 7.1 Lead 已改（CI 配置，`/.github/**`）

`deploy.yml` 的 `test` job：
1. 新增 `redis:7-alpine` service（含 healthcheck）。
2. `Wait for PostgreSQL` → `Wait for PostgreSQL and Redis`，
   并给 `pg_isready` 补上 `-d agent_room_test`
   （避免回退成 runner 的 OS 用户角色，即 `FATAL: role root does not exist`）。
3. job 级 env 改用**数字 IP `127.0.0.1`** 而非 `localhost`（第二道防线），
   并补 `MAPR_TESTING=1`、`MAPR_TEST_REDIS_URL=redis://127.0.0.1:6379/15`。
4. 新增"Prove real PostgreSQL and real Redis are wired (no silent skip)"步骤，
   断言 dialect 是 postgresql、Redis 可达、且用的是专用 DB 15。

`audit-round4-ci.yml`：把 `MAPR_DATABASE_URL` / `MAPR_TEST_DATABASE_URL` /
`MAPR_TEST_REDIS_URL` 中的 `localhost` 一并改为 `127.0.0.1`。

两个文件均已用 `yaml.safe_load` 验证可解析，并核对了 job env / services / steps 结构。

### 7.2 待完成（测试隔离，真正的根因修复）

仅把 DSN 换成数字 IP 属于"掩盖"而非"修好"。必须同时**收窄 DNS stub 的作用域**：
让三个文件的 stub 只对测试目标 host 返回合成 IP，其余 host（含数据库与 Redis 主机）委托真实 resolver。
覆盖文件：
`test_a2a_egress_ssrf_linux.py`、`test_agent_url_ssrf_linux.py`、`test_a2a_protocol_v1_linux.py`。

验收要求为**双跑**：DSN 用 `localhost` 与 `127.0.0.1` 都必须全绿；
并做反向验证（恢复旧 stub 作用域时 `localhost` 必须重新出现 `TimeoutError`）。

## 8. 残余不确定性

- 本报告未取得"审计 CI 后端 job 的失败清单逐条原文"，
  只核到它的**失败步骤**与 Deploy 一致；
  由于两者的 DSN 都是 `localhost` 且跑同一套件，判定为同一根因。
  如需 100% 确证，需要该 job 的日志（当前匿名 API 无权限，仓库内也没有对应 zip）。
- `deploy.yml` 的改动无法在本地真实执行 GitHub Actions；
  已通过 YAML 结构校验 + 本地复刻"接线验证"步骤（`OK: PostgreSQL dialect = postgresql | Redis DB = redis://127.0.0.1:6379/15`）
  来降低风险，最终仍需一次真实 CI 运行确认。
