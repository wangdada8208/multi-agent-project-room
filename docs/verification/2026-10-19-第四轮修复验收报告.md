## 3. 根因一（24 + 1 = 25 项）：DNS stub 劫持了数据库连接

### 机制

1. CI 两个工作流的 DSN 都用主机名 **`localhost`**。
2. SSRF 测试用例 monkeypatch `socket.getaddrinfo`，**对任意 host 都返回合成公网 IP**。
3. 于是 asyncpg 解析 `localhost` 时拿到 `93.184.215.14`，去连 `93.184.215.14:5432`（黑洞）
   → 60 秒超时 → `TimeoutError`。
4. `127.0.0.1` 是 IP 字面量，asyncio 走 `_ipaddr_info` 快路径**完全不查 DNS**，
   所以本地用任何 stub 都复现不出来。**这就是"本机全绿、CI 全红"的全部原因。**

真实日志 traceback 与之吻合：`asyncpg/connection.py:2497` → `compat.timeout` →
`asyncio/timeouts.py:117 raise TimeoutError from exc_val`。

### 决定性实验（同一用例，只改 DSN 主机写法）

| DSN 主机 | 结果 |
| --- | --- |
| `127.0.0.1` | `1 passed in 0.49s` |
| `localhost` | `1 failed in 60.98s`，`E TimeoutError` |

### 修复（双层，缺一不可）

1. **测试层（根治）**：收窄 stub 作用域。新增
   `conftest.py::REAL_GETADDRINFO` / `is_infrastructure_host()` / `fake_agent_dns()` /
   `protect_infrastructure_hosts()`，让基础设施 host（localhost、IP 字面量、
   DSN 里的主机）走真实解析，只有合成的 agent 主机名被 fake。
   接入点：`test_a2a_egress_ssrf_linux.py`(2)、`test_agent_url_ssrf_linux.py`(8)、
   `test_a2a_protocol_v1_linux.py`(4，**用户只提到 1 处，实际 4 处**)。
2. **CI 层（第二道防线）**：两个工作流的 DSN 改用数字 IP `127.0.0.1`。

**SSRF 断言一条未削弱**：覆盖矩阵、`dns_calls` 计数、`connections`、SNI/TLS 断言全部保留；
没有任何 skip/xfail。

### 验收双跑（原文）


## 4. 根因二（5 项）：Deploy 的 test job 根本没有 Redis

`deploy.yml` 的 `test` job 原本只有 postgres service，**没有 redis**，
且 `Run tests` 只设了数据库 DSN 与 `PYTHONPATH`，**没有 `MAPR_TESTING` / `MAPR_TEST_REDIS_URL`**。

代码依据：`rate_limit.py:129` 只要 `MAPR_TEST_DATABASE_URL` 存在就判定为测试环境；
`_get_effective_redis_url()`（`:138-149`）在缺 `MAPR_TEST_REDIS_URL` 时回退到
`settings.redis_url`（默认 `redis://localhost:6379/0`）并改写为 DB 15
→ `localhost:6379` 拒连 → Redis 不可用 → `_get_redis_sync()` 返回 `None`
→ `scan_iter` 上的 `AttributeError`。

修复：`deploy.yml` test job
①新增 `redis:7-alpine` service（含 healthcheck）；
②`pg_isready` 补 `-d`（避免回退成 OS 用户角色）；
③job 级补 `MAPR_TESTING=1`、`MAPR_TEST_REDIS_URL=redis://127.0.0.1:6379/15`；
④新增"Prove real PostgreSQL and real Redis are wired (no silent skip)"步骤
（断言 dialect=postgresql、Redis 可达、用专用 DB 15）。

该步骤已在本机实跑通过：
`OK: PostgreSQL dialect = postgresql | Redis DB = redis://127.0.0.1:6379/15`

## 5. 根因三（2 项）：真实 H3 缺陷

### 5.1 P0：comparison_username 未在模型与写入路径维护

已确认的最初缺陷（用户判断正确）：迁移 `i90c20261017` 加了
`users.comparison_username`（`nullable=False, server_default=""`）+ 唯一索引，
但 `User` 模型无此字段、注册路径不写它 → 迁移后所有新账号比较键都落 `""`
→ **第二个不同名账号就会被数据库拒绝**。

修复：
- `app/models/user.py`：新增字段映射；`__table_args__` 声明
  `Index("ux_users_comparison_username", unique=True)`（与迁移同名，SQLite 的
  `create_all()` 形状因此与真实迁移一致）；`@validates("username")` 同步维护；
  **`default=""` 改为按行推导的 `_default_comparison_username`**
  —— 这堵住了我复审时发现的**同类缺口**：Core/bulk 写入（`users.insert()`）
  绕过验证器时会全部落 `""`，正是原 P0 的翻版。
- `app/auth/routes.py`、`app/chat/service.py`：两处 `User(...)` 构造点显式写入。
- 不回写存库 username（`comparison_identity` 只作比较键）。

**独立验证（不依赖同事断言）**：`scripts/verify-p0-independent.py`
在**真实 `alembic upgrade head` 迁移过的库**上打真实端点：

### 5.2 migration-vs-test 脱节（用户第三优先项）已修

新增 `backend/tests/test_migration_after_upgrade_linux.py`：**不走 `create_all()`**，
而是建一次性独立库 → `alembic upgrade head` → 验证 → `DROP DATABASE`。覆盖：
A 连续两个不同名都成功；B 标点变体只允许一个；C 唯一索引存在且值正确；
D h80 后插老行再 upgrade 验证回填。SQLite 明确 skip 并写明原因。

旧断言 `test_normalized_username_has_unique_index` 已按设计改为验证
`ux_users_comparison_username`（用户"测试检查了错误的列"的判断正确）。

### 5.3 顺带修掉的两个真实缺陷

**（a）`/ready` 探针在 PG 上事务 abort、原因被掩盖**
`check_database_readiness` 探针失败后**未 rollback**，PG 事务进入 aborted 状态，
后续 `SELECT 1 FROM users` 报 "current transaction is aborted"，
探针返回误导性的 `DATABASE_UNAVAILABLE`，而非设计中的原因。
SQLite 不会 abort 事务，所以默认测试路径**长期掩盖**了它。
已加回滚 + 定向回归测试，并做变异验证（去掉 rollback 该测试立即失败）。

**（b）可导致 HTTP 500 的用户名边界（本轮新发现）**
`ß` 属于 `\w`，casefold 后变 `ss`（**变长**）。64 个 `ß` 的用户名能通过 pydantic 校验，
但归一化后是 128 字符，超过 `String(64)` → 插入报错 → **500 Internal Server Error**。
已在 `RegisterRequest` 增加 `field_validator`，归一化键超长时返回 **422**。
实测：32×ß（键长 64）仍 **200**（不过度拒绝）；40×ß、64×ß 由 **500 → 422**。
