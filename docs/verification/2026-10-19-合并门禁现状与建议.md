## 2. 建议（需要人类在仓库设置中执行，属于高风险操作，须先获批准）

以下为仓库设置变更，按项目规矩（`AGENTS.md` 规则 3）需要人类批准；
智能体不应也无法自行开启。建议按优先级实施：

### 2.1 在 main 上启用必需状态检查（最高优先）

对 `main` 分支启用保护规则或 ruleset，要求下列检查通过后才允许合并：

| 必需检查 | 来源工作流 | 为什么需要 |
| --- | --- | --- |
| `Backend (real PostgreSQL + real Redis + Alembic)` | `audit-round4-ci.yml` | 后端全量套件，本轮 32 项失败就出在这里 |
| `Frontend (vitest + build)` | `audit-round4-ci.yml` | 前端测试与生产构建 |
| `Repository hygiene` | `audit-round4-ci.yml` | 空白字符与密钥扫描 |
| `Safety guard (no main push / no deploy)` | `audit-round4-ci.yml` | 防止审计工作流误触发部署 |
| `test` | `deploy.yml` | 部署前门禁；它失败时 build/deploy 会被跳到 |

注意：`audit-round4-ci.yml` 当前**只由 `workflow_dispatch` 与 `pull_request` 触发**，
没有 `push` 触发，因此它的检查名只在 PR 上出现——
这正是它适合作为"合并前门禁"的原因。

### 2.2 其他建议

1. **要求分支与 main 保持最新**（Require branches to be up to date），
   避免用陈旧的绿色检查合并新代码。
2. **禁止 force push 与删除 main**。
3. **要求至少 1 名评审通过**，且不允许作者自审通过。
4. 把 `deploy.yml` 的 `test` job 视为**部署门禁**而非可选检查：
   它现在已补齐 Redis 与接线验证（见
   `docs/verification/2026-10-19-CI-32项失败根因与证据.md` 第 7 节）。
5. 长期建议：把审计 CI 的检查也接入 `push`→`main`（例如作为 `deploy.yml`
   的一个 job），这样合并后的 main 也有独立的全量验证，
   而不必依赖 PR 时刻的检查结果。
