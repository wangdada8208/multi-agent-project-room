## H1 — 访问日志泄露裸 token（High）

**现象**：`uvicorn.access` 记录 `GET /api/v1/invites/inv_xxxSECRET`，邀请 token 原样进日志。

**代码现状**（已读）：
- `backend/app/core/observability.py:87` `_INLINE_SECRET` 只匹配 `token=…` / `token: …` 形式的 `key=value`；`:82` `_BEARER_AUTH` 只匹配 `Bearer xxxxx`。
- 访问日志字符串形如 `"GET /api/v1/invites/inv_abc123 HTTP/1.1" 200`，没有 `key=`，两条规则都不命中。
- 真实路由：`backend/app/api/invites.py:91` `GET /api/v1/invites/{token}`；同族 `:115` `POST /api/v1/invites/{token}/redeem` 同样把 token 放在路径里。

**修复方案（两处一起做，防御纵深）**：

1. 脱敏层（必须）：`backend/app/core/observability.py` 新增路径段规则
   ```python
   # /api/v1/invites/<token>[/redeem] 与查询串里的 ?token= / ?access_token=
   _PATH_SECRET_SEGMENT = re.compile(
       r"(?i)(/api/v1/invites/)[^/\s?#]+"
   )
   _QUERY_SECRET = re.compile(
       r"(?i)([?&](?:token|access_token|invite|key)=)[^&\s\"']+"
   )
   ```
   在 `scrub_text()` 里先跑这两条，分别换成 `\1***REDACTED***`。
   注意：只锚定**已知的敏感路由前缀**（邀请），不做"任意长随机串都打码"，避免把 room_id / 正常路径打坏。

2. 路由层（建议，同时做）：`invites.py` 一次性把 token 移出 URL 路径——
   `GET /api/v1/invites/{token}` 改名为 `GET /api/v1/invites/detail?token=…`，`POST /api/v1/invites/{token}/redeem` 改为 `POST /api/v1/invites/redeem` + body `{"token": …}`。
   查询串和 body 都会被现有 `_INLINE_SECRET` / `is_sensitive_key` 覆盖。
   **代价**：前端调用点需要同步改，属于前后端联动，需要跟协作室-前端对齐后一起提。

**复现命令**（审计提供的探针，需要在工作机上跑；本机未验证其存在性）：
```bash

# 修复前预期 exit=1
```

**现象**：`race_x_bot` 与 `race_x-bot` 并发注册，两者都返回 200，各建一个账号（3/3 复现）。

**修复方案**：

1. 模型：`user.py:18` 改为 `unique=True, index=True`（唯一索引同时承担查询索引）。

## H2 — 测试隔离缺陷导致全量 30 failed（High，验收阻断）

**现象**：`pytest backend/tests` → 755 全绿；`pytest backend/tests tests` → 30 failed（13 个 `test_pg_dual_hub_linux.py` + 17 个 `test_pg_room_hubs_linux.py`），典型错误 `WebSocket 握手 HTTP 403`。

**根因（本次核对代码后定位，审计当时未定位到）**：

子进程 Hub 用的是一套**独立 PG 库**（`MAPR_DATABASE_URL` 子进程单独给），WebSocket 403 = `handle_chat` 里 `close(code=4003)` 被判成"用户身份未授权 / 房间不存在 / 房间无权"（`backend/app/chat/ws_handler.py:236/259/270`）。也就是说，**业务数据在创建它的那个进程/那次会话里看不到**。

最可能的机制组合：
1. **跨进程不可见**：`actors` fixture 在 pytest 进程里建用户和房间；Hub 子进程另起 uvicorn、用自己的连接池读同一个库。库名不同或提交时机不同，就会 403。
2. **事件循环边界**：审计已排除并发、库残留、启动时序、单一路径，且"4 个根目录测试文件单独与 hubs 同跑均通过"——说明触发条件跟**同一次会话里先跑过谁**有关（`tests/` 下的用例会改写 `MAPR_DATABASE_URL` 等环境变量或 `core_database.async_session` 指向），子进程的 `env = os.environ.copy()`（`test_pg_room_hubs_linux.py:82`）把被污染的变量带给了 Hub。
3. 若出现"另一个同名 `conftest.py` / 另一个 `actors` fixture 被解析到"的情况，`from conftest import ...` 取到的会是**先被 import 的那个模块**（Python 模块缓存），指向另一套 engine。

**修复步骤（按顺序，每步单独验证）**：

1. **定位**：先加只读诊断，不改业务代码。
   ```bash
   pytest tests backend/tests/test_pg_room_hubs_linux.py -x -q -k 'test_ordinary_user' 2>&1 | tail -40
   # 失败时读 tmp_path 里 hub-*.log，确认 403 的具体 reason
   ```
   在 `handle_chat` 三个 4003 分支里把 `reason` 带进日志（`logger.warning` 只记 reason 与 room_id，不记 token），重跑看是哪一条。
2. **隔离 `sys.path`**：在 `test_pg_room_hubs_linux.py` 与 `test_pg_dual_hub_linux.py` 里，把 `from conftest import ...` 改为显式加载同目录 conftest：
   ```python
   import importlib.util as _ilu
   _spec = _ilu.spec_from_file_location("_local_conftest", Path(__file__).with_name("conftest.py"))
   _local = _ilu.module_from_spec(_spec); _spec.loader.exec_module(_local)
   isolated_engine, sessions = _local.engine, _local.test_session
   ```
   （或改用 `pytest_request.getfixturevalue` 传入 `engine`/`test_session`，彻底不依赖模块名。）
3. **子进程环境白名单**：`env = os.environ.copy()` 改为从 `isolated_engine.url` 与显式常量重建（`MAPR_DATABASE_URL`、`MAPR_ENVIRONMENT=test`、`PYTHONPATH`、`PYTHONDONTWRITEBYTECODE`），**不继承**其余 `MAPR_*`；避免 `tests/` 里改过的变量泄进子进程。
4. **就绪判据加强**：等待 `/health` 200 之外，再等 `actors` 数据在子进程可见（例如先请求一个"公开房间列表/邀请详情"接口，确认能读到 `actors.room`），读到才开始连 WS。这样失败会报"数据不可见"而不是含糊的 403。
5. **conftest 一致性**：`backend/tests/conftest.py` 的 `setup_db` 只 `create_all(Base.metadata)`；如果某个测试文件 import 了额外模型表（如 `app.models.room_share`），只有 import 发生在那次会话里才会建表。统一改为**在 conftest 顶部一次性 import 全部模型**（`app.core.database` 里 `init_db` 的那份清单），然后**删掉**各测试文件里逐条 `import app.models.xxx` 的补丁。这一步也正好回答组长问的"conftest 那行未提交改动"：那行 `from app.models import room_share as _room_share_models` 正是这个临时补丁，按第 5 步统一收进 conftest 后**就不再需要**，可以丢弃这行本地改动。

**复现命令**：
```bash

python -m pytest backend/tests -q                                    # 修复前：755 passed
python -m pytest backend/tests tests -q                              # 修复前：30 failed, 766 passed
```

**修完怎么验证**：
1. 三条复现命令：前两条仍全绿；第三条 **0 failed**。
2. 连续跑 3 次结果一致（审计环境每次约 84 秒）。
3. 反向确认失败可见：临时把子进程 `MAPR_DATABASE_URL` 指向错误库，测试必须**失败且报"数据不可见"**，不能静默通过——防止修成"跳过即通过"。
4. CI（`.github/workflows/audit-round4-ci.yml:180` 正是 `pytest backend/tests tests`）backend 作业转绿。

**风险**：低（只动测试基础设施）；但第 5 步会让部分"靠各文件自己 import 才建表"的用例暴露真实依赖，可能出现少量连带失败，需要一个一个改成显式声明，不能靠 `skip` 糊过去。

## 追加：只读分享链接与搜索词（2026-10-17，前端反馈后补）

### 顺带修掉的一个真实缺陷（后端自己发现）

原实现用 `new is not old` 判断"参数是否被脱敏"。字符串同值但不同对象时（`str` 子类、动态拼接、超长串）会误判为"已脱敏"，导致**整条无害日志被打成 `***REDACTED***`**，排障信息全丢。已改为 `not (new is old or new == old)`，并加用例 `test_unter_redacted_arg_does_not_mask_whole_record` 锁定。

### 关于"前端把正文放网址"这条风险（组长要求确认）

后端核对结论：
1. 前端发消息走 WebSocket 消息体，正文不进网址；
2. 生产镜像 `backend/Dockerfile:23` 与 `scripts/start.sh:6` 都是 `--no-access-log`，`frontend/nginx.conf:7` 是 `access_log off`，**线上两层目前都不记访问日志**。

因此：**眼下没有泄露路径，但"日志关着"不是安全边界**。一旦有人为了排障打开访问日志，正文或搜索词进了网址就会立刻泄露。建议作为验收条款：任何入站接口不得接受正文走查询串或路径段，并保留本轮脱敏作为纵深防御。是否立这条，由组长定。
