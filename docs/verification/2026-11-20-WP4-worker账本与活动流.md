## 交付内容

### 1. 哈希链账本（ledger.ts）

- `LedgerEntry` 新增可选链字段 `seq?: number`、`prev_hash?: string`、`entry_hash?: string`；
  `buildLedgerEntry` / `appendLedger` / `readLedger` / `LedgerKind` / `LedgerEntry`
  对全部既有调用方保持向后兼容（`buildLedgerEntry` 不产链字段，签名不变）。
- `appendLedger` 按解析后的文件路径串行（与 `secureFile.ts` 相同的 writeChains 模式），
  并发追加不会把链写成两条分叉；目录 0700、文件 0600（`mkdir mode` + 显式 `chmod`，与 secureFile 一致）。
- 每次追加从文件末尾向前找最后一条带完整链字段的 entry；
  无链文件或纯遗留行一律从 `seq=1, prev_hash="GENESIS"` 起链（`LEDGER_GENESIS_PREV_HASH`）。
  调用方自带的 seq/prev_hash/entry_hash 一律丢弃重算，伪造字段进不了链。
- `entry_hash = sha256(prev_hash + "|" + canonicalStringify(entry 去掉 entry_hash))`，
  canonicalStringify 复用 `./canonical.ts`；seq 与 prev_hash 均在哈希覆盖范围内。
- `verifyLedger(file, {anchoredCheckpoint?})` 与 `verifyLedgerEntries(entries, ...)`：
  - 无链字段的行如实计为 `legacy_unverified_entries`，不宣称追溯防篡改；
  - `entry_hash_mismatch`（内容被改）、`prev_link_mismatch`（重排/断链）、
    `sequence_gap`（序号缺口）、`chain_fields_incomplete`（链字段被部分剥除）、
    `unchained_after_chain`（链已开始后混入无链行）、`malformed_line`（非 JSON 行）；
  - 传入锚点（`{head_seq, head_hash}`，`SignedLedgerCheckpoint` 可直接赋值）后检测
    `anchor_truncated`（链头落后于锚点）、`anchor_missing`、`anchor_hash_mismatch`（锚点后整段被重写）。
  - 自校验（无锚点）对「整体截断」与「整段重写后重算哈希」如实不可见——这正是需要签名检查点的原因，
    测试里两条路径都覆盖并注明。

### 2. 签名检查点（activity.ts）

- `SignedLedgerCheckpoint` = 规范负载 `{version:1, room_id, stream_id, head_seq, head_hash, entry_count, created_at}`
  + `signer` + `signature`。
- `signLedgerCheckpoint(input, privateKey)` / `verifyLedgerCheckpoint(checkpoint, expectedSigner?)`
  用 viem `privateKeyToAccount` / `verifyMessage`（与 `grant.ts` 同一风格），
  消息为 `"MAPR1-LEDGER-CHECKPOINT " + canonicalStringify(payload)`；
  验签结果 `{ok:true,signer}` 或 `{ok:false,reason:malformed|wrong_signer|bad_signature}`。
- `checkpointFromVerification(verifyResult, {room_id, stream_id})` 把链头转成待签名负载，
  `entry_count` = 链上 + 遗留的全部已解析条目数。

### 3. 安全元数据事件（activity.ts）

- `buildSafeActivityEvent(input)` 输出严格白名单
  `{id, room_id, actor_kind, actor_id, kind, subject_id, status, created_at}`；
  `actor_kind` 限 `human|agent|helper|system`，各字段有非空与长度上限校验。
- 输入出现 `payload/payload_hash/content/params/params_hash/digest/body/to/from/cc/bcc/subject/text/html/recipients/raw/message`
  任一键直接抛错——宁可报错也不让正文或参数摘要混进元数据管道（Hub 红线）。

### 4. 本地活动查询（activity.ts）

- `queryLocalActivity(entries, filter?, opts?)` → `{entries, total, integrity}`。
- 过滤：`actor`（匹配 peer 或 sender，不区分大小写）、`kind`（单个或数组精确匹配）、
  `status`（`ledgerEntryStatus` 按 kind 映射的粗粒度状态 pending|ok|denied|failed|expired|uncertain，
  `Record<LedgerKind, ActivityStatus>` 全量映射，新增 kind 时编译器强制补映射）、
  `since`/`until`（ISO 含边界）、`limit`（取最近 N 条，返回仍按时间序）。
- `integrity`：默认对传入数组跑 `verifyLedgerEntries`；可用 `opts.verification` 复用
  `verifyLedger(file)` 的文件级结果（含 malformed_lines 与锚点校验），
  `opts.anchoredCheckpoint` 也可直传。

## 遗留（如实记录）

- `verifyLedger` 自校验无法发现「文件整体截断」与「锚点后整段重写并重算」——设计上依赖
  周期性签名检查点锚定（测试已覆盖两种情况）。检查点签名本身由 `verifyLedgerCheckpoint` 验，
  `verifyLedger` 只消费 head_seq/head_hash，不做签名校验（调用方先验签再当锚点传入）。
- `verifyLedger` 的行号以「解析后第 N 条」计；存在损坏行时与物理行号有偏移（issue 注释已写明）。
- 上报器（把元数据事件 + ledger_head 锚批量上行）未做——依赖 m2 迁移与 Hub 端点，需人类批准。
- ownerConsole `GET /api/activity` 挂载未做——ownerConsole* 在并行 worker 边界内，由集成方挂接；
  本包交付的 `queryLocalActivity` + `verifyLedger` 即为该端点的现成数据源。
- 双机/真网验收未做，本包全部验证为单元级。
