## 优先修复项

### 01｜P0：本机授权页将外部 URL 参数直接拼成 HTML

位置：`workers/xmtp-member/src/ownerConsole.ts:111`。

`app_id`、`scope`、`purpose` 未转义就替换进 HTML；CSP 同时允许内联脚本。临时 HTTP 服务复现：传入无害 `<script>` 标记，返回 HTML 保留完整脚本，响应策略允许其执行。

影响：若主人打开恶意构造的授权链接，注入脚本可以在本机网关同源上下文访问接口，破坏“主人点击批准”的边界。这是由源码与 HTTP 复现推导的攻击影响，本轮未针对真实主人网关进行浏览器攻击。

建议：移除这三处服务端 HTML 字符串替换，用文本节点展示参数；严格校验申请字段，并收紧脚本策略。回归应覆盖三个字段的 HTML 注入。

### 02｜P1：登录用户能越过房间权限读写知识库

位置：`backend/app/knowledge/routes.py:24`。

知识库端点仅检查登录和房间存在，没有调用 `require_role`。隔离 ASGI 复现：房主创建房间与文档后，另一个非成员的权限查询返回 403，但读取该文档和创建新文档均返回 200。

影响：房间知识库没有实现预期的成员隔离。Git 端点也未检查房间权限，且 GitService 不按 room_id 选择仓库；该部分为源码发现，未进行生产数据读取。

建议：读操作校验 viewer，写操作校验 member；作者绑定认证主体；逐一核查文件、任务、审批、仓库端点的对象权限。

### 03｜P1：浏览器私钥金库没有进入实际房间流程

位置：`frontend/src/pages/RoomPage.tsx:120`、`frontend/src/lib/xmtpLocalIdentity.ts:24`。

房间仍调用 `loadOrCreateInboxKey`，直接把完整私钥写入 localStorage 的 `mapr-xmtp-inbox-key`。加密、解锁函数只有测试调用，没有页面调用。

生产 JS 也包含明文存储键，不含金库存储键 `mapr-xmtp-vault`，与本机调用关系一致。

建议：接通首次设置口令、后续解锁与旧明文身份的加密迁移；迁移确认前不能直接删除旧身份，避免失去原群访问能力。验收必须从真实页面检查存储，不只测试密码学函数。

### 04｜P1：生产前端缺少创建加密房间所需的 worker 配置

位置：`frontend/src/pages/RoomPage.tsx:129`、`frontend/Dockerfile:7`、`.github/workflows/deploy.yml:100`。

创建新加密群时强制校验 `VITE_XMTP_WORKER_ADDRESS`。镜像构建没有注入该变量；本机 `.env.local` 未跟踪，不在 CI checkout 中。实际公网 JS 中校验函数被传入 `void 0`。

影响：生产页面尝试为未绑定房间建群时，会在该校验点抛出 `worker address required`，且页面只 console.error，没有可操作的错误提示。已有绑定群不一定受此项影响。

建议：确认成员身份配置的产品方式，并在镜像构建中提供需要的公开配置；增加新房间从创建到第一条加密消息的发布验收。若改为动态成员发现，须先按项目规则评审架构提案。

### 05｜P1：邮件收据请求在真正经过协议后无法通过范围校验

位置：`workers/xmtp-member/src/envelope.ts:155`、`outgoingRequest.ts:8`、`cli.ts:82`、`policy.ts:54`。

`email.receipt` 的策略校验要求 `constraints.query`，但通用 request 解码只保留 date_from/date_to。发请求构造器和 CLI 也没有完整传递 query。

复现：构造含 `query: "from:12306"` 的合法请求，encode→decode 后 query 消失，随后 checkRequest 返回 out_of_scope。

建议：形成范围对应的请求约束契约，贯穿 CLI、控制台、构造、解码、签名和连接器；相关协议接口调整需先提交可审阅提案。测试必须真的经过编解码，而不是直接调用连接器。

### 06｜P1：代理自助接入只有部件，没有运行闭环

位置：`workers/xmtp-member/src/cli.ts`、`joinRequest.ts`、`onboardingFlow.test.ts:37`、`backend/app/api/invites.py:115`。

邀请兑换 API 只更新 used_at、返回 group id 和 scopes，不会把成员加进 XMTP 群。CLI 没有邀请兑换/入群命令；生产入口未调用 `applyJoinApproval`。该函数只在测试中被直接调用。`onboardingFlow.test.ts` 手工构造 inviteProposedScopes，再直接更新策略，未经过真实邀请 API 或 XMTP 入群。

建议：补齐“取得邀请→证明身份→兑换→房主侧添加群成员→更新允许范围→新成员收发”的入口及失败恢复；不要把获取 group id 当成已经入群。

### 07｜P1：协调任务缺轮次更新、去重及结果归属检查

位置：`workers/xmtp-member/src/handleEnvelope.ts:126`、`taskStore.ts:9`。

已复现：

- 连续 round 1/2/3 结果全部被拒，仍发送 round 2/3/4 任务，最终状态 retrying。原因是 TaskStore 中 task.round 保持 1，nextStep 每次读旧轮次；round 4 又会被收件方的协议校验拒绝。
- 同一任务消息处理两次，模型被调用两次，没有执行侧 request_id/round 去重。
- 对目标执行者派出的任务，用另一个发送者及另一个 conversationId 交结果，仍可被评为 completed。运行入口有总体发送者白名单，但没有任务执行者及会话绑定校验；其他白名单成员仍能触发此问题。

另外，解析验收模型失败时实际走 retry，任务书要求 escalate。重试任务也没有带回 challenge，执行者难以根据审查意见修正。

建议：先固定任务状态及轮次契约，再补持久化去重、发送者/会话/当前轮次/终态校验、三轮上限和失败升级。成员端任务状态没有 canceled，也没有取消消息及中止模型调用路径；旧 A2A/trusted_runner 的取消保护不能证明这条 XMTP 路径同样有保护。

### 08｜P1：Connect 默认弹窗不返回结果，安全回调也未完成

位置：`workers/xmtp-member/src/ownerConsoleHtml.ts:250`、`frontend/src/components/ConnectButton.tsx:30`。

只有存在 redirect_url 才给 opener 发消息。演示页面的两个按钮均未传 redirectUri；批准后的分支只 alert、close。用真实页面内联脚本与假的 DOM/opener/fetch 复现：批准后 opener 收到 0 条消息。因此父页面 onSuccess 不会触发，连接中状态不结束。这是脚本行为复现，未宣称完成真实浏览器 E2E。

同时，发送端 postMessage 使用 `*`；接收端不检查 event.origin、event.source 或请求关联标识，只要 type 相符就接受成功消息，也未验证签名、数据哈希、接收方及有效期。

Connect approve 不关联持久待批准申请，也不记录消费状态。相同合成请求 POST 两次，均 200，连接器调用两次。max_uses=1 只是签名字段，Connect 侧没有完整兑现“使用一次即废弃”的流程。

建议：先跑通默认弹窗批准/拒绝/关闭/超时，再绑定应用来源、回调来源、弹窗对象与单次申请。签名核验及消费规则需要明确归属后实现。

### 09｜P1：过期同意在定时清理前仍可批准

位置：`workers/xmtp-member/src/consentActions.ts:30`、`index.ts:321`。

approveConsent 先 claim approved，没有按 created_at 同步检查 10 分钟 TTL。过期只由每 30 秒清理一次的定时器处理。用多年前的 pending 申请复现，批准仍返回 ok:true。这影响刚过期至下一次清理的窗口，也影响重启后旧队列。

连接器失败发生在已标记 approved 之后，返回 no_connector，申请无法正常重试。发送失败同样没有完整“待核实/安全重试”状态。

建议：执行前同步复核有效期，分别表达批准、取数、发送、失败及待核实，不能仅依赖定时器或一次 approved 状态。

### 10｜P1：连接器有隐私与结果真实性缺口

位置：`workers/xmtp-member/src/connectors/gmailReceipt.ts:96`、`googleCalendar.ts:65`。

合成数据复现：邮件主题中的手机号/邮箱、附件文件名中的邮箱原样返回，只有 body_excerpt 脱敏。attachment_sha256 实际是 attachmentId 或 filename 的哈希，不是附件内容 SHA256，不能用于附件完整性核验。

Google freeBusy 返回 HTTP 200 但 calendars.primary.errors 有错误时，仍当成 busy:[] 返回，可能把“查询失败”误报为“全部空闲”。

建议：所有披露字段统一脱敏；真实下载获批附件后计算内容哈希，或准确改名为标识哈希；明确检查分日历错误。真实 OAuth/token 刷新及真实账号流程本轮未验收。

### 11｜P1/P2：部署配置与发布门禁需要收紧

位置：`.github/workflows/deploy.yml:124`、`docker-compose.yml:10`。

- runner 无 Docker 权限时尝试 `chmod 666 /var/run/docker.sock`，会给本机所有用户 Docker 控制权限。已确认代码存在；本轮未登录服务器确认当前 socket 实际权限。
- Compose 将 PostgreSQL 5432 绑定所有地址，默认密码有 password 回退值。生产是否被防火墙隔离、是否覆盖密码，本轮未核验，不能据此断言数据库公网已暴露。
- 部署没有版本及功能健康检查或自动回滚；部分复制、拉取、兼容 SQL 失败通过 `|| true` 忽略。主服务更新发生在迁移之前，迁移失败缺少显式恢复步骤。
- CI 未运行成员测试、成员 typecheck、前端测试、真实用户流程。backend/tests/conftest.py 强制使用 SQLite，因此“CI 有 PostgreSQL 服务”不代表所有后端 API 测试都跑在 PostgreSQL。

建议：使用明确的 runner Docker 权限配置；数据库端口最小暴露；补迁移备份/失败恢复、版本健康检查及三组件测试门禁。实际服务器权限修改、迁移、部署仍须按 AGENTS.md 单独授权。

## 后续体验与验收改进

- 加密房间只订阅消息流，没有显式加载该群历史；切房间也未按 room_id 清空/隔离全局 messages。需验证刷新回放、断网补偿、跨房间内容隔离。缺 group id 时流筛选没有阻断，可能暂时混入该身份其他会话消息。
- 页面“已连接”来自 Hub WebSocket，不证明 XMTP 或主人网关可用。应分别显示真实状态，并提供 worker 未配置、未进群、网关未启动等可操作错误。
- Git/知识库/文件/任务面板需在 XMTP 产品路径重新逐项验收，确认展示的是当前房间和当前执行者的数据。
- 统一 PLAN、ROADMAP、总路线、README、ARCHITECTURE、AGENTS 和验收表。当前“全部完成”“阶段未开始”“生产历史房间待清理”等互相冲突；旧基线 f1af097 只能标为历史。数据库已迁移不能自动证明历史明文数据已清理。
- 不应继续以勾选或测试名称判断阶段完成。每项完成记录至少区分：已实现、自动测试、真实联调、生产验证、主人验收。

## 建议的下一里程碑

先完成 01–04 的授权、房间隔离、私钥和生产配置修复；然后补齐 D/E/F 用户入口与 C/B 状态边界；最后做一次当前版本的双机全流程验收。

验收链：两位主人各自准备网关与身份 → 新建房间 → 邀请真正入群 → 双向加密消息与刷新回放 → 请求忙闲/邮件并批准、拒绝、过期 → 协调任务三轮以内完成或升级 → 中途取消并阻断迟到结果 → 重发/断网/重启恢复 → 第三方弹窗取得经过核验的结果。

使用虚构数据完成权限与故障验收后，再在单独授权下做真实账号验证。本审查不是架构修改、数据库迁移或生产部署批准。
