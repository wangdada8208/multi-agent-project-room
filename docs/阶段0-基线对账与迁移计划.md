## 3. 客户端执行体迁移方案

系统当前存在两套客户端脚本。
两套脚本均未达到可信协作的生产标准，必须在阶段 1 完成整合与演进。

### 现有组件对比

| 评估维度 | 旧适配器 `local_agent_adapter.py` | 新网关 `agent_gateway.py` |
| --- | --- | --- |
| 代码规模 | 1022 行，逻辑较为复杂 | 310 行，结构较为精简 |
| 通信机制 | 依赖 WebSocket 长连接与补发逻辑 | 依赖 HTTP 轮询接口 |
| 进程隔离 | 混杂系统调用与直接执行 | 采用 ACP 模式，通过标准输入输出隔离 |
| 审批时机 | 先调用大模型，后匹配关键词补发审批 | 尚未实现审批流拦截 |
| 取消机制 | 仅做内部标记，未联动终止外部进程 | 仅捕获退出信号，未联动服务端任务取消 |
| 身份绑定 | 支持令牌登录，但未校验智能体归属 | 仅做简单注册，缺乏严格归属认证 |

### 迁移裁决

1. 废弃 `local_agent_adapter.py` 中的执行调度逻辑。该脚本的先执行后审批机制存在安全漏洞，不得作为未来协作的基础。
2. 保留并吸收 `local_agent_adapter.py` 中的断线重连与消息补发机制。
3. 以 `agent_gateway.py` 的子进程模式作为执行层的基础骨架。将其升级为符合标准协议规范的真正受控运行器。
4. 在阶段 1 统一产出 `trusted_runner.py`。新运行器必须在向子进程发送输入前强制校验授权凭证，在收到取消指令时立即杀掉进程组。

## 4. 十大核心失败场景对账表

依据指导意见第 10 节的要求，系统对当前代码在异常边界下的表现进行了摸底。

| 序号 | 故障场景 | 当前代码现状 | 阶段 1 改造与验收目标 |
| --- | --- | --- | --- |
| 1 | 无效或已撤销凭据、冒用其他智能体、非法访问房间 | 已有全局令牌校验，但缺乏智能体从属绑定 | 增加会话与智能体双向签名，越权访问直接返回 403 并阻断 |
| 2 | 错误主人批准、批准后篡改协商请求参数 | 仅记录了批准动作，未对原请求哈希签名 | 引入一次性结构化授权凭据，参数被篡改时授权自动失效 |
| 3 | 重复消息投递、消息乱序、丢失确认 | 依赖数据库自增主键，无业务层消息去重 | 引入客户端唯一消息流水号，重复投递直接幂等忽略 |
| 4 | 数据落库失败、服务器或运行器异常崩溃 | 采用事务提交，但网络断开可能导致假死 | 增加落库前置握手与明确失败重试协议，不假报已送达 |
| 5 | 工具已在本地执行但结果未成功存盘 | 当前直接将异常作为错误消息返回 | 标记任务为待核实状态，严禁在无二次授权时盲目重跑 |
| 6 | 智能体等待主人审批期间断线或重启 | 进程重启后上下文丢失，审批状态悬挂 | 审批状态持久化入库，重启后能够根据任务标识无缝恢复 |
| 7 | 主人生成期间撤销、执行中取消、迟到响应返回 | 取消仅变更任务状态，底层进程依然在后台运行 | 发送取消时直接终止子进程，迟到输出一律直接丢弃 |
| 8 | 对方智能体发来越权指令或诱导披露其他资料 | 当前直接将对方输入喂给模型 | 引入严格的输入类型标记，外部消息严禁触发特权工具 |
| 9 | 对方单方声称达成共识、模型故障、预算耗尽 | 前端依赖文本标记匹配，无法抵御伪造 | 共识必须由双方智能体携带主人数字凭证分别确认 |
| 10 | 升级了新认证的服务器与未升级的旧客户端混用 | 旧客户端可能绕过新鉴权接口 | 废弃非认证旧接口，旧客户端连接时直接返回明确升级提示 |

## 5. GitHub 仓库代码同步建议

两名开发者若要实现真正的代码与基线同步，建议采取下列步骤：

1. 保持 `origin/main` 作为受保护的稳定主干。
2. 开发者将当前包含 53 个通过测试、前端优化与核心开发文档的代码集，推送到 GitHub 的特定协作分支（例如 `codex/phase0-baseline`）。
3. 协作者从该分支拉取最新成果，在本地执行 `pytest backend/tests` 与 `npm run build`。
4. 双方在本地均复现 53 个测试全绿与前端构建成功后，在 GitHub 发起向 `main` 的拉取请求并共同确认合并。
